# ルールとラーニングループ

ルールは、エージェントの仕事の仕方を形作る、残る散文の指示です。ラーニングループはその書き方です。ワークフロー中にエージェントを直し、ステージの承認ゲートでその直しを確認すると、フレームワークが保存します。同じ直しを二度しなくて済みます。

この章は利用者向けの案内です。ルールの置き場所、5 層の積み方、ラーニングループが直しを取る流れ、ルールと並んで決まった第二意見を出すセンサーです。スキーマ寄りの仕組みは、その都度 Developer Reference へリンクします。

---

## ルールの概観

ルールは、アクティブスペースのメモリ層 `aidlc/spaces/<active-space>/memory/` の Markdown です。ワークスペースルートに手で直せる一式があり、どのハーネスもネイティブ include で読みます（Claude の `@`-import スタブ、Kiro CLI の resources か IDE の steering、Codex の `AIDLC_RULES_DIR`、opencode の `instructions` グロブ、Copilot の `AGENTS.md` `@`-import）。ファイル名がスコープです。

```
aidlc/spaces/<active-space>/memory/
├── org.md                 # framework + organization-wide defaults
├── team.md                # your team's affirmed practices
├── project.md             # this project's specialization
└── phases/
    ├── ideation.md
    ├── inception.md
    ├── construction.md
    └── operation.md
```

ファイル内に `scope:` フィールドはありません。スコープはファイル名です。`org.md` はフレームワーク既定（トランクベース開発、テストの姿勢、walking-skeleton 方針）。`team.md` はチームが認めたプラクティス。`project.md` はこのプロジェクト固有。4 つの `phases/<phase>.md` は、そのフェーズの全ステージに効くルールです。例: inception のフェーズルールは、アーキテクチャ判断に代替を少なくとも 2 つ書け、と要求します。

中身は見出しの下の平文です（`## Way of Working`、`## Testing Posture`、`## Deployment`、`## Code Style` など）。読んで、手で直せます。フレームワークが書くのはラーニングループ経由です。

スキーマ、ファイル名とスコープの対応、解決の仕組みは Developer Reference の [Rule System](../reference/08-rule-system.md) です。

---

## 5 層の鎖

ワークフロー開始時、ルールは 5 層の鎖で解決されます。

```
org → team → project → phase → stage
```

モデルは **厳格加算** です。当たるルールは全部、エージェントのコンテキストに出ます。実行時に黙って落としたり上書きしたりしません。組織既定、チームプラクティス、プロジェクト固有は連結です。ステージがフェーズを宣言しているので、対応するフェーズルールが付きます。（5 層目のステージ単位ルールは、将来のリリース用に空けてあります。）

以前の版からの意図した変更です。`overrides:` ブロックも `enforcement:` キーワードもありません。当たる層は同時に全部あり、実行時リゾルバに調停させず、残す学びの衝突は受理時にオーケストレータが見ます（後述の [受理時の衝突検査](#admission-time-conflict-checks)）。

鎖の解決はワークフロー開始時に **一度** です。フレームワークがステージ定義、ルール、センサーを一つのグラフにコンパイルするときです。以降、エージェントは解決済みの見え方を読みます。途中で鎖を歩き直しません。そのコンパイル境界は、この章末のプレーン模型と同じです。[プレーン: 全体の収まり](#planes-how-it-fits-together) を見てください。

---

## ラーニングループ

ラーニングループは、一度の直しを残るルールにする仕組みです。大半のステージ実行では何も足しません。それで健全です。ループが走るのは、ステージ中に出たものを、残す価値があると人が決めたときだけです。

人から見える瞬間は 4 つです。ステージ中にエージェントが日記を付け、ゲートが候補を出し、残すものを人が確認し、フレームワークが次回用に書きます。

### memory.md の日記

ステージ実行中、フレームワークは観察ログを `<record>/<phase>/<stage>/memory.md` に積みます。インテントのレコードディレクトリ `aidlc/spaces/<space>/intents/<YYMMDD>-<label>/` の下です。エンジンが run-stage ディレクティブを出すときに、配布テンプレートから作り、オーケストレータが維持します。手編集しません。見出しは次の 4 つです。

- **Interpretations** — ステージ散文が曖昧で、エージェントが選んだ解釈
- **Deviations** — ステージ散文から意図して外した箇所と、その理由
- **Tradeoffs** — 検討した代替と、選んだ理由
- **Open questions** — 次回までに確認したいこと、まだ不確かな文脈

各エントリに時刻が付きます。言語モデルがステージ中に `memory.md` へ観察を書き、受理時にオーケストレータが後述の節単位の衝突比較をします。決定論的なツールが候補を取り出し、ゲートで人が明示して残したものだけを書きます。

### ゲートの儀式

各承認ゲートの前に、フレームワークはラーニングゲートを走ります（プロトコルでは §13 の儀式）。候補は 2 系統から集め、一つの確認リストにします。

1. **エージェントの日記を原文のまま出す。** 決定論的ツールが `memory.md` を読み、4 見出しの下の空でない行を、出典見出し付きの候補にします。言い換えも、「面白いもの」のフィルタもありません。書いた行が出ます。
2. **自由記述の口は常に聞く。「Anything to add for next time?」** 観察を書き、4 見出しのどれかを選びます。人に求める分類はその見出し選びだけです。

残したい候補にチェックを付けます。そのステージの `memory.md` が空なら、日記を付けたかどうかの宣誓は求めません。フレームワークが静かに記録して先へ進みます。

### 残した学びの行き先

パスは人が選びません。見出しが行き先を決めます。

- Interpretations、Deviations、Tradeoffs は、`aidlc/spaces/<active-space>/memory/project.md` のプラクティスになります（確認した学びはプラクティスそのもの）。トピック見出しの下です。
- Open questions は昇格しません。調べ物であり、入れるルールではありません。

既定スコープは **project** です。ワンクリックの「promote to team」で、残した学びを `memory/project.md` から `memory/team.md` へ広げられます。このプロジェクト以外にも効くときです。org へ広げる道はありません。org ルールはフレームワーク同梱か、別プロセスで組織が書くものです。ラーニングループは org スコープには書きません。いちばん狭いスコープを既定にすると、一つのプロジェクトの驚きが組織ルールになる事故を防げます。

確認した学びはプラクティスです。載るのは practices-discovery が認めるのと同じ、アクティブスペースのメモリファイル（`aidlc/spaces/<active-space>/memory/project.md`、`team.md`）です。転がる `*-learnings.md` という別面はありません。入り方のライフサイクルが違います。practices-discovery は節ごとを決定論的に認め、ラーニングループはゲート経由で、日付付き・トピック見出し付きのエントリを一つずつ追記します。

残す学びがルールではなく **センサー結び** のとき（ステージ出力に新しい決定論的検査を走らせたいとき）、フレームワークは 2 書きを原子的にします。センサーマニフェストの足場を作り、その id を起点ステージの import リストへ追記します。日記、ゲート確認、結果のファイル書き込みは、それぞれ監査行（`RULE_LEARNED` または `SENSOR_PROPOSED`）を残します。ルールが黙って入ることはありません。

<a id="admission-time-conflict-checks"></a>

### 受理時の衝突検査

残す学びがディスクに載る前、ゲートプロトコルはオーケストレータに、`memory/org.md` の対応節との比較を求めます。節単位の LLM 検査です。提案が org ルールと矛盾すれば、オーケストレータは衝突している文を引用し、エントリを直す、スキップする、org ルールの所有者へ上げる、を聞きます。衝突が無いもの、または人が上げたものだけが、決定論的な書き込みへ渡ります。`aidlc-learnings.ts persist` は `org.md` を独自に見ず、衝突を判定せず、渡された選択を受け取ります。org 矛盾のエスカレーションは、リゾルバ入力の一貫性を保つ監査の助けであり、強制の境界ではありません。

practices-discovery の確認ゲートは、この org 衝突検査を走りません。昇格は、人の確認で正当化された決定論的な節置換です。チームやプロジェクトのルールがディスクに載った*あと*に org 方針が変わったときは、`/aidlc --doctor` が要求に応じてそのドリフトを出します。ファイル、節、衝突している org の文を名指しするので、チームが動けます。doctor 検査は助言で、止めません。助言行 2 種は [CLI コマンド](12-cli-commands.md) と [トラブルシュート](15-troubleshooting.md) です。

### 効くのは次のワークフロー。途中からは変わらない

あるゲートで取った学びは、**今のワークフローの残りには効きません。** この実行では会話でエージェントを直済みです。ルールは次回用です。新しい行はディスクにありますが、進行中のワークフローは開始時にコンパイルした見え方を持ち続けます。

次にワークフローを始めると、コンパイルが新しいファイルを読み、ステージ 1 から効きます。ルータが BGP から得る安定と同じです。パケット飛行中に経路は作り直さず、AI-DLC もワークフロー途中では再コンパイルしません。見返りは予測可能性です。先に承認したゲートは安定したルール集合に対する証言であり、進行中の実行の足元をフレームワークは変えません。

## 通しの例: ANZ 銀行プロジェクト

端から端まで、具体的な一周です。

Sam が ANZ 銀行プロジェクトで `/aidlc feature` を走ります。ワークフローは `requirements-analysis` に着きます。Sam はステークホルダーメモに "the transaction shouldn't duplicate on retry" と書きます。銀行取引、処理中の支払いの意味です。プロダクトエージェントは "transaction" をデータベーストランザクションと読み、ACID 意味論の要件だと解釈します。Sam が直します。エージェントは成果物を更新して続けます。

フレームワークはこれを予測していません。ANZ 固有の用語ルールも、一般語とドメイン語の衝突を拾うセンサーもありません。エージェントが曖昧さに当たっただけです。

**1. 日記が残す。** フレームワークは `<record>/inception/requirements-analysis/memory.md` の `## Interpretations` の下に追記します。

```
- 2026-05-21T09:14:32Z — Stakeholder note used "transaction"; interpreted as
  database-transaction. Sam corrected to mean banking-transaction (the payment
  being processed, not the DB write). Worth flagging for ANZ project context.
```

ルールはまだ入りません。エージェントの日記だけです。

**2. ゲートが出す。** ステージが終わります。承認ゲートの前に、ラーニングゲートが `memory.md` を読み、その解釈行を候補にします。「Anything to add for next time?」も聞きます。Sam は transaction 用語の候補にチェックを付けます（Interpretation → `memory/project.md` に載る）。自由記述も足します。「エージェントが AWS アカウント用語に寄りがちだった。銀行の顧客実体は常に 'ANZ customer' と呼ぶべき」。見出しは Deviation を選び、同じ `memory/project.md` へ行きます。

**3. 衝突検査が走る。** オーケストレータが両方を、節単位の LLM 検査で org プラクティス（`memory/org.md`）と比べます。「ANZ transaction」も「ANZ customer」も org ルールの対象外なので通ります。決定論的ツールが provenance 付きで両行を `memory/project.md` に書き、監査ログはそれぞれ `RULE_LEARNED` を残します。

**4. 今のワークフローは変わらない。** ステージは承認され、ワークフローは `user-stories` へ進みます。新しい行はディスクにありますが、このワークフローのコンパイル済み見え方には入りません。この実行では、Sam がステージ中に直済みです。

**5. 次のワークフローが拾う。** その日のうちに Sam が `/aidlc bugfix` を走ります。ワークフロー開始のコンパイルがスペースメモリ層を歩き、`memory/project.md` を取り、全ステージのコンテキストに載せます。bugfix のステージ 1 から、エージェントは "transaction" が支払いであること、顧客実体が "ANZ customer" であることを知っています。

払ったコストは一度です。ゲート確認 1 回、ファイル書き込み 1 回。以降のワークフローでは、ディレクトリ走査にもう 1 ファイル乗るだけで戻ってきます。

## センサー: 決定論的な第二意見

ルールはエージェントが読む散文です。センサーは、エージェントがステージ出力を書いたときに自動で走る決定論的検査です。ルールが「ユーザーストーリーは Given/When/Then」と言えば、センサーは必要な見出しがファイルに実際にあるかを、バイト単位で確かめられます。ルールはステージへエージェントを送り、センサーはエージェントが実際に出したものを返します。

### センサーの発火

ステージ中にエージェントが出力を Write / Edit すると、PostToolUse フックがそのステージに当たるセンサーを見て、一致するものを走ります。一致はファイルの形です。コード品質センサーが `**/*.{ts,js}` を解析すると宣言すれば、TypeScript と JavaScript の書き込みだけで発火します。任意のステージ出力で発火する文書形状センサーは、フィルタを省略します。ワークフロー中にセンサーを手で呼びません。Write と Edit のたびに付いてきます。

このリリースのセンサー結果は **助言** です。失敗は監査行と、欠けているものを指す詳細ファイルを残しますが、ステージの承認ゲートもワークフローも止めません。信号は見えます。どうするかは人です。

### 監査ログに出るもの

センサーの動きは、インテントの `audit/` シャードに `Sensor Fired`、`Sensor Passed`、`Sensor Failed` の行として出ます。失敗行は詳細ファイルへリンクします（例: `<record>/.aidlc-sensors/<stage-slug>/required-sections-<timestamp>.md`）。欠けた見出し、参照されていない上流成果物、lint エラーなど、具体的な隙間です。監査ログは [状態と監査](10-state-and-audit.md) です。

### フレームワーク同梱のセンサー 6

同梱は 6 つです。

| センサー | 発火対象 | 検査内容 |
|--------|----------|--------|
| `claim-sources` | Intent Capture のレコードディレクトリ出力 | 主張ごとに見えるソースタグがあること。登録した説明、ワークフロースコープ、メモリ本文が権威ある入力と一致すること。残した仮定が明示確認と一字一句一致すること |
| `required-sections` | レコードディレクトリの任意の markdown 出力 | 必要な H2 見出しがあること（汎用の内容形状検査） |
| `upstream-coverage` | レコードディレクトリの任意の markdown 出力 | ステージの成果物集合が、消費すると宣言した上流成果物を、slug、wikilink、または産出ステージのディレクトリパスで参照していること |
| `traceability` | `traceability.json` のステージ成果物 | 安定した上流 ID が宣言され被覆されていること。status と target が妥当なこと。決定論的な下流 target があること |
| `linter` | `.ts` / `.js` のコード出力 | 設定したリンタを包む（既定は ESLint） |
| `type-check` | `.ts` / `.tsx` のコード出力 | 設定した型検査を包む（既定は `tsc`） |

各ステージは、出力のどれでどのセンサーが発火するかを宣言します。自作も足せます。`.claude/sensors/` にマニフェストを書き、走らせたいステージへ id を足します。ラーニングループでも、ゲートで確認すればセンサーを入れてくれます。マニフェスト形式、ステージごとの行列、書き方の通しは [Sensor System](../reference/07-sensor-system.md) です。自分のプロジェクトへ足す手順は [カスタマイズ](13-customization.md) です。

## プレーン: 全体の収まり

上のことは、プレーンを意識しなくても使えます。ただ下の設計はネットワークの規律を借りていて、名前を付けると「次のワークフローから効く」が腹に落ちます。

現代のルータは仕事を 3 プレーンに分けます。AI-DLC も同じ分け方です。

- **コントロールプレーン** — *何が走るべきか* のスキーマ。ステージ定義、ルール、センサー。ネットワークで言えば経路計算です。設定から、何がどこに当たるかを決めます。一度しか走らないので、遅くて賢くて構いません。
- **データプレーン** — *実際の実行*。ステージ実行、エージェント起動、インテントのレコードディレクトリのファイル。ネットワークで言えばパケット転送です。速く、繰り返し、照合です。データプレーンは解決済みの答えを読み、自分では導き直しません。
- **マネジメントプレーン** — *観察と設定* の面。`/aidlc --doctor`、監査ログ、`CLAUDE.md`。人が触る速さで、ここで設定し、ここで照会します。

コントロールプレーンは、ワークフロー開始時にルールとセンサーをグラフへ **一度** コンパイルします。以降のデータプレーンは、そのグラフから解決済みの答えを読みます。だからワークフロー途中で取った学びは、次のコンパイル待ちです。フレームワークは答えを「トポロジ変更時」（ワークフロー開始）に計算し、「パケット時」（ステージごと）には計算しません。結果は、再現できる実行と、再起動後のきれいな復旧です。

利用者としては、たいてい横一枚ずつ触ります。ワークフローを走る、学びを残す、チームプラクティスを寄せる、何が起きたかを監査する。各枚は下のプレーンに触れますが、プレーンそのものを考えさせません。模型全体、コンパイル境界、復旧の性質は [Plane Architecture](../reference/02-plane-architecture.md)、それが出すテレメトリ成果物は [Runtime Graph](../reference/13-runtime-graph.md) です。
