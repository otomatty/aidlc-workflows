# スコープ

スコープはダイヤルです。ある種類の仕事で、フレームワークの 33 ステージのうち *どれが* 走り、どれが外に座るか。バグ修正に市場調査や環境プロビジョニングは要りませんが、デプロイパイプラインと実行ステージは走ります。規制のあるエンタープライズ機能はライフサイクル全体が要ります。毎回ステージを手で選ばせるのではなく、AI-DLC は名前付きスコープを 11 同梱します。それぞれが全ステージ集合に対する厳選した EXECUTE / SKIP 判定で、深度、テスト戦略、任意のレビュー上限といったワークフロー既定と対になります。スコープを選べば、残りは流れます。

ハーネスエンジニアにとってスコープは純粋なデータです。ほかの原語と同じく、ファイルとして書きます。半分は 2 つです。`core/scopes/aidlc-<name>.md` ファイル 1 本（身元、ルーティング用メタデータ、ワークフロー既定）と、ステージごとの所属タグ（各ステージの frontmatter `scopes:` 一覧が、走るスコープを指名）です。スコープの追加や調整に TypeScript は要りません。この章はワークフローです。スコープの材料、チームスコープの足し方、既存の調整、ツールが見てくれるものと残すものです。

ユースケースと利用者が読むルーティング表付きの 11 スコープ目録は、User Guide の [Scopes, Depth, and Test Strategy](../guide/05-scopes-and-depth.md) です。この章は、同じデータの書く側です。

## スコープの材料

スコープは 2 か所に書きます。切れ目が考え方そのものです。スコープの *身元* は自分のファイルにあり、*所属*（どのステージがその下で走るか）はステージ側へ転置されます。

**1. スコープファイル — `core/scopes/aidlc-<name>.md`。** スコープごとに 1 ファイル。`core/sensors/` と同じ形です。`feature` スコープの frontmatter は次です。

```yaml
---
name: feature
depth: Standard
keywords: []
description: Full lifecycle for new features, practical depth
skeleton: on
---

# feature scope

Prose intent: why these stages, why skip those.
```

スコープ frontmatter のフィールドは:

| フィールド | 必須 | すること |
|------------|------|----------|
| `name` | はい | スコープ名。コアファイルは `aidlc-<name>.md`。プラグインのスコープファイルはステムが `name` と一致 |
| `depth` | はい | 既定の詳細レベル — `Minimal`、`Standard`、`Comprehensive` |
| `testStrategy` | いいえ | 深度と独立したテスト量の上書き。既定は `depth` に合わせる |
| `review_cap` | いいえ | このスコープ下の最大レビュークラス: `adversarial`、`advisory`、`none`。無いときはスコープ単位の下げ無し。cap は下げられても、ステージの `review_class` を上げることはありません。自律スウォームのレビューはステージの宣言クラスを保ちます |
| `keywords` | いいえ | `/aidlc <自由文>` 自動検出の自然言語トリガー。平らな文字列一覧はブロック（`- item`）でもフロー（`[item, item]`）でもよい。空一覧はオプトアウト |
| `description` | いいえ | `/aidlc --help` に描く一行。（SKILL.md のコンパイル済みスコープ表は Scope / Depth / TestStrategy / EXECUTE / Total だけを示し、description は出しません） |
| `skeleton` | いいえ | `on` は、プラクティスがスコープ依存のとき walking-skeleton の儀式へスコープを入れる。`off` または無しはオプトアウト |
| `runner` | いいえ | `true` は既定の生成スコープランナー集合にスコープを入れる |
| `freeform_default` | いいえ | 好ましいコア既定（`classic`）が有効でないとき、選択を意識したフォールバックとしてこのスコープを指名 |
| `change_control` | いいえ | スコープの Change Control 既定。`strict` または `relaxed`。人が承認または確めたあとに入力が変わったときの振る舞い（strict は承認を開き直す。relaxed は変更を一度記録し、人に一行で伝え、続ける）。無しは strict。同梱の既定は `enterprise`、`security-patch`、`infra` が strict、残りは relaxed。メモリ層の `## Change Control` 節（`Mode: strict`）は、どのスコープ既定も、インテントごとの切り替えにも勝ちます。[Change Control](../guide/13-customization.md#change-control) |

ローダーはファイル横断の重複したスコープ `name` を落とし、エラーで両方のファイルを指名します。

### 自由文の既定

`freeform_default: true` は、プラグイン選択のあと内部の `classic` 既定が使えないとき使うスコープを、インストールが指名できるようにします。指名は、有効プラグインが一つだけのフォールバックより先に検査されるので、スコープをいくつか持つプラグインは、アルファベット最初のスコープを受け入れる代わりに、細い既定を選べます。

**有効** なスコープが `freeform_default: true` を宣言してよいのは最大 1 つです。選んだコア / プラグイン集合に請求者が複数あると、グラフコンパイルは失敗し、請求者を全部指名します。無効プラグイン上の請求は、それらが一緒に有効になるまで衝突しません。フィールドは明示タイポを直しません。未知の `AWS_AIDLC_DEFAULT_SCOPE` 値は、それでも検証を落とします。

### Walking-skeleton 既定

任意の `skeleton:` フィールドは、スコープ依存の walking-skeleton 姿勢を制御します。`skeleton: on` は、チームの `## Walking Skeleton` プラクティスが `scope-dependent` に解決するとき、このスコープの Construction が walking-skeleton の儀式で開くという意味です。`skeleton: off` は、最初のボルトが普通のボルトとして走るという意味です。無しは off が既定なので、合成 / 実行時承認のスコープとプラグインスコープは、明示してオプトインしない限りスケルトンボルトを conjure しません。

### Change Control 既定

任意の `change_control:` フィールドは、このスコープの新しいインテントが始める値です。作成時に状態ファイルへ `- **Change Control**: <value> (from scope <name>)` として書かれます。人はその 1 インテントについて `/aidlc --change-control <value>` または普通のチャット依頼で切り替えられます。この行が無い古いインテントは、明示して設定するまで strict のままです。次の新しいインテントは、またスコープ既定から始まります。リポジトリの全員に値を持たせるには、スコープファイル 11 を直さないでください。メモリで一度宣言します（`aidlc/spaces/<space>/memory/org.md`、`team.md`、または `project.md` の `## Change Control` に `Mode: strict`）。メモリの `strict` はどのスコープ既定にも勝ち、ファイルを指名してチャットやフラグの切り替えを拒みます。メモリの `relaxed` や節が無いことは効果がありません。2 値以外の検証エラーはファイルと許される値を指名します。インテントごとのコマンドは、無効な状態行を直します。

**2. 所属タグ — 各ステージの `scopes:` frontmatter。** ステージは、自分が走るスコープを自分の frontmatter で指名します。`core/aidlc-common/stages/<phase>/<slug>.md`:

```yaml
scopes:
  - enterprise
  - feature
  - mvp
```

スコープを指名するステージはその下で `EXECUTE`、無いのは `SKIP` です。パッケージは各ステージの `scopes:` 一覧を、コンパイル済み EXECUTE / SKIP グリッド `<harness-dir>/tools/data/scope-grid.json` へ *転置* します。グリッドは実行時が読む、無視される生成投影です。手で直したりコミットしたりしません。初期化ステージ 3 つはどのスコープも指名します（いつも走ります）。

理解する価値のある判断が一つあります。`depth` と `testStrategy` の関係です。深度は各ステージの成果物がどれだけ詳細を運ぶかを制御します。テスト戦略は生成されるテストの数を制御します。独立なのは意図的です。同梱スコープの多くは `testStrategy` を外し、`depth` から継ぎます。`classic` は Standard / Standard、`express` は Minimal / Minimal。`workshop` は Standard 深度と Minimal テストで明示の切れ目を示します。スコープが切れ目を欲しいなら両方を宣言します。各レベルの意味は User Guide の [The 3 Depth Levels](../guide/05-scopes-and-depth.md#the-3-depth-levels) と [The 3 Test Strategy Levels](../guide/05-scopes-and-depth.md#the-3-test-strategy-levels) です。

フィールドごとの契約全体 — `keywords` が単語境界でマッチする仕方、曖昧な自由文起動をアルファベットスコープのタイブレークが解決する仕方を含む — は Developer Reference の [Contributing § Adding a Scope](../reference/11-contributing.md#adding-a-scope) です。この章は判断を要約します。あの節が規範の仕様です。

## スコープとステージの関係

スコープとステージは反対の端から互いを指します。両方の向きを持っておくと助かります。

**ステージ**は自分の身元を宣言します。フェーズ、リードエージェント、消費する成果物と出す成果物、そしていま、走るスコープ（`scopes:` 一覧）。**スコープ**は自分の身元、ルーティング用メタデータ、ワークフロー既定を自分の `.md` ファイルで宣言し、中にステージごとの所属はありません。所属はステージ側です。両者の結びはスコープ名です。新しいステージを足すとき（[ステージを足す](02-adding-a-stage.md)）、スコープ所属は *そのステージに* 置きます。`scopes:` 一覧が、走らせるスコープを全部指名します。スコープを指名しないステージはどこでも `SKIP` です。コンパイル時の転置がそれらのステージごとの一覧をグリッドにするので、所属は一度、ステージ側に書き、11 の別々のスコープブロックで再宣言しません。

その分離は、このガイドの残りが乗るデータ対コードの線と同じです（[ハーネスエンジニアガイド](00-overview.md)）。スコープファイルは *身元* についてのデータ。ステージの `scopes:` 一覧は *所属* についてのデータ。コンパイル済みグリッドは両者の転置です。

## チームスコープを足す

チームが `hotfix` スコープを欲しいとします。`bugfix` より細く、緊急の本番パッチ向け。回帰テストとデプロイだけ欲しい。変更は新しいスコープファイル、走らせる各ステージへの `scopes:` タグ、再生成したローカル投影です。下の規律を映してください。検証手順とコマンド行の全体は [Contributing § Adding a Scope](../reference/11-contributing.md#adding-a-scope) です。

### 手順

1. **`core/scopes/aidlc-hotfix.md` を置く。** いちばん近い既存スコープ `aidlc-bugfix.md` をコピーし、frontmatter を直します。`name: hotfix`、`depth` を選び、自由文自動検出が欲しいなら `keywords`（`[hotfix, urgent]`）、ヘルプ文の `description`、スコープ依存の Construction 儀式既定の `skeleton: on|off`、これが選んだインストールの一意なフォールバック指名であるときだけ `freeform_default: true`、`depth` からずらすべきときだけ `testStrategy`、スコープがステージレビューを下げるべきときだけ `review_cap`。意図を説明する短い散文本文を書きます。

2. **`hotfix` の下で走らせるステージにタグを付ける。** `EXECUTE` にしたい各ステージ（`core/aidlc-common/stages/<phase>/` の下）の frontmatter `scopes:` 一覧に `hotfix` を足します。タグしないステージはそのスコープで `SKIP` です。初期化ステージ 3 つは含めなければなりません（いつも走ります）。

3. **再生成。** `bun scripts/package.ts` を走らせ、無視されるハーネス投影を作り直します。`scope-grid.json` とコンパイル済みスコープ表を含みます。`bun scripts/package.ts --check` を走らせ、独立したソースのみのビルド 2 つがバイト一致することを確めます。

4. **スコープが解決し、受け入れられることを確める。** `/aidlc --doctor` を走らせます。それから、新しいスコープの下の init が正しい `Scope:` 行の状態ファイルを出すこと、環境既定として、途中の `--scope` 変更として受け入れられることを確めます。

5. **キーワード推論を確める**（`keywords` を埋めたときだけ）。トリガーの一つを含む自由文が、`feature` へ落ちるのではなく新しいスコープを検出することを確めます。

6. **スコープを意識する文書を更新し、ルーティングテストを足す。** いくつかの文書はスコープを手で列挙します。User Guide のスコープ参照とルーティング表、カスタマイズ章の有効値一覧、オーケストレータ参照のスコープ対ステージ写像。同じ変更で更新します。既存スコープが使わない型でステージを飛ばすなら、既存のスコープごとのテストを模型にしたワークフローテストを足します。

7. **（任意）打てるランナーを生成する。** スコープはファイルが着地した瞬間から `/aidlc --scope <name>` で完全に使えます。ランナーは要りません。一言コマンド（`/aidlc-hotfix`）が欲しいなら、スコープ frontmatter に `runner: true` を足し、`aidlc engine gen runners scopes` を走らせます。`aidlc engine gen runners scopes --all` はそのフラグに関係なく、どのスコープファイルにも `skills/aidlc-<scope>/SKILL.md` を出します。各ランナーは薄いシェルで、スコープを焼き込んだ `aidlc-orchestrate next --scope <name>` を `done` まで駆動し、「関係ない新しい仕事を始める？」節に、`/aidlc` オーケストレータと同じ認識、提案（`AskUserQuestion`、決して自動作成しない）、`next --new-intent --scope <name>` 案内を運びます。ランナーはすでに走れるスコープを包装し、定義はスコープファイルです。`hooks:` ブロックは持ちません。決定論の背骨（監査、センサー、rebuild-stage-graph、状態検証）は `settings.json` でプロジェクト全体に登録されているので、どのランナーも無料で継ぎます。スコープファイルを足すまたは改名するたびに、生成器（または `scopes --check`）を再走させてください。

### 自動で検証されるもの

この実装は実行時に `.claude/scopes/*.md` の存在から有効スコープ一覧を `validScopes()` 経由で導くので、ファイルが着地した瞬間に多くが収まります。

- スコープは一度にどこでも有効です。`init`、`--scope` 変更、環境既定の解決、`doctor` は全部同じヘルパーを見るので、どれもコード編集を要しません。
- エラーメッセージは変更無しであなたのスコープをアルファベット順に列挙します。
- `keywords` を付けたなら、frontmatter 一覧が埋まった瞬間に自由文 `/aidlc <text>` が自動検出します。SKILL.md の散文編集は無し。表の再生成だけです。
- パッケージはいつも現行のステージ YAML からグリッドを導くので、古いローカル生成バイトはリリース入力ではありません。

### 自動では検証しないもの

- **タイポしたスコープ名の `scopes:` タグはそれでもパースします。** `hotfix` ではなく `hotfx` を指名するステージ frontmatter はきれいにコンパイルします。誰も聞かないグリッド列を出すだけです。捕まえは、`validScopes()` が `.md` ファイルから導くので、ファイルが無いスコープは起動時に拒まれることです。しかしステージ上の打ち間違えたタグは、本物のスコープからそのステージを黙って落とします。`/aidlc --doctor` とスコープごとのテストがガードレールです。
- **古いローカル投影は手検査を誤らせます。** ステージの `scopes:` を直して、無視される古い `dist/` 木を使い続けると、そのローカル実行時はまだ古いグリッドを含みます。ローカル実行時の検査の前に再生成してください。CI とリリース組み立てはいつもソースから作り直します。
- **スコープごとのフェーズ列カバー。** 同梱のフェーズ列テストは、既知スコープ名のハードコード一覧を反復します。新しいスコープはその一覧を伸ばすまで行使されません。同じ変更でスコープを足してください。
- **手で保つ文書。** 文書を grep してくれるものはありません。スコープ参照、ルーティング表、カスタマイズの有効値一覧は散文です。スコープファイルと自分で揃えてください。

## 既存スコープを調える

調整は小さい編集ですが、着地するのはスコープではなくステージです。よく出る変更は 2 つです。

- **ステージを入れる、または外す。** ステージの `scopes:` 一覧にスコープ名を足す、または外す。たとえば、チームが初回でもいつも監視を結ぶので、`observability-setup` の `scopes:` に `mvp` を足す、という手です。タグ 1 つ、それから `bun scripts/package.ts` で再生成し、`--doctor` を走らせます。
- **既定の深度、テスト戦略、またはレビュー上限を変える。** スコープの `core/scopes/aidlc-<name>.md` frontmatter で `depth` を直し、`testStrategy` を足す / 外す、または `review_cap` を足す / 外す。最初の 2 つは成果物とテスト量を再較正します。`review_cap` はステージのレビュークラスを `adversarial`、`advisory`、または `none` へ下げ、決して上げません。各スコープが自分の既定を運ぶので、変更はスコープを選ぶどのワークフローにも効きます。実行ごとの `--depth`、`--test-strategy`、`--review` は対応する振る舞いをさらに下げられます。

どちらでも、上の手順 3 の再生成と doctor の対が効きます。編集は小さい。検証は同じです。

層についての注: 同梱スコープを調えるのは、フレームワーク同梱ファイルを直接直すことです。ステージの `scopes:` タグ、または同梱の `core/scopes/aidlc-*.md`。フォークが違う既定を欲しいときは正当ですが、`aidlc-` 系譜を運ぶファイルを変えていること、フレームワークのアップグレードがそれらを揃えたいかもしれないことに注意してください。チーム固有の振る舞いが欲しく、ほかの人が頼る既定に触れないときは、同梱 11 の隣に正味新しいスコープファイルを足す方がきれいです。
