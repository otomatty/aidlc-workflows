# チームナレッジ

ナレッジは、エージェントが仕事の前に読む領域の文脈です。コーディング標準、アーキテクチャの好み、領域の用語集、チームが落ち着いたパターン。ハーネスのうち、フレームワークが強制する拘束ではなく、エージェントが読むファイルを足して形を作る部分です。この章は、その文脈をエージェントに渡すワークフローです。ファイルの置き場所、どのエージェントが見るか、ナレッジとルールのあいだの判断です。

[ルールとラーニングループ](05-rules-and-the-loop.md) を読んだなら、区別を通して持ってください。ルールはフレームワークが強制する立ち振る舞い、ナレッジはエージェントが仕事中に秤にかける参照です。どちらもエージェントの振る舞いを形作りますが、乗るプレーンが違い、載り方も違います。

---

## 二層: フレームワークのナレッジと、あなたのもの

AI-DLC のナレッジは二層に分かれ、直してよいのは片方だけです。

**第 1 層 — 方法論ナレッジ** は、この実装と同梱で `.claude/knowledge/` の下にあります。各エージェントがステージを走らせるための方法論参照です。`aidlc-architect-agent/architecture-guide.md`、`aidlc-developer-agent/code-generation-guide.md`、横断は `aidlc-shared/`。**触らないでください。** これらのファイルは、フレームワークのアップグレードのたびに上書きされます。そこに足したものは、チームが新しい版を取るときに消えます。

**第 2 層 — チームナレッジ** はあなたものです。スペース単位の `aidlc/knowledge/`（`aidlc/spaces/<space>/knowledge/` の略）にあり、スペースの `memory/`、`codekb/`、`intents/` の隣です。1 インテントのレコードに閉じ込められず、スペースのどのインテントでも積み上がります。会社固有の標準、方針、約束を持ちます。フレームワークは上書きしません。エンジンは最初の `/aidlc` で空の `aidlc/knowledge/` ディレクトリを作るだけで、中身はあなたに残します。埋めるのはこのディレクトリです。（エージェントが秤にかける参照ではなく、フレームワークが *強制* すべき立ち振る舞いのプラクティスは、代わりにスペースのメモリ層 `aidlc/spaces/<active-space>/memory/` です。）

二層の切れ目は、このガイドのほかが乗るデータ対コードの線を、ナレッジに当てたものです。フレームワークは方法論を所有し、あなたは自分の文脈を所有し、アップグレードは片方を、もう片方に触れずに置き換えられます。両層のディレクトリ形の全体は [Knowledge System → Two-Tier Architecture](../reference/10-knowledge-system.md#two-tier-architecture) です。

## チーム全体か、エージェント固有か

第 2 層は、約束としてエージェント配置に従います。`aidlc-shared/` ディレクトリと、エージェントごとのディレクトリ 1 つ。全部スペース単位の `aidlc/knowledge/` の下です。ファイルを置く場所が、どのエージェントが載せるかを決めます。

| 置き場所 | 載せる主体 | 用途 |
|----------|------------|------|
| `aidlc/knowledge/aidlc-shared/` | **どの** エージェントも、どのステージでも | 横断の標準。命名、コミット形式、プロジェクトの領域用語集 |
| `aidlc/knowledge/<agent>-agent/` | **その** エージェントだけ、アクティブなリードのときだけ | 1 役の領域文脈。アーキテクト向けのアーキテクチャパターン、devsecops 向けのセキュリティ方針 |

ディレクトリ名はエージェント slug と正確に一致しなければなりません。`architect/` ではなく `aidlc-architect-agent/`。ディレクトリ名の誤字は、ファイルが黙って無視されるいちばん多い理由です。フレームワークはエージェント自身のディレクトリを名前で歩き、何も見つけず、エラーなしで先へ進みます。エンジンはこれらのサブディレクトリを作ってくれません。`aidlc/knowledge/` はブートストラップ時に空です（後述）。正確な slug で、各ディレクトリを自分で作ってください。

`aidlc-shared/` に手を出すのは、標準が本当に 11 エージェント横断で効くときだけです。アーキテクトにだけ効くパターンは `aidlc-architect-agent/` です。アーキテクチャステージに文脈を足し、ほかのエージェントの窓を薄めません。User Guide の [Adding Company Standards worked example](../guide/08-knowledge.md) が、ディレクトリ作成、執筆、確認まで端から端の通しです。最初のファイルを書く前に一度読む価値があります。

各ディレクトリの用途のエージェントごとの表は [Knowledge System → Adding Team Knowledge](../reference/10-knowledge-system.md#adding-team-knowledge) です。

## エージェントがナレッジを載せる仕方

ナレッジファイルを登録したり、どこかに結んだりしません。正しいディレクトリにあることが登録です。ステージが始まると、コンダクターは固定の 6 手順で文脈を載せ、第 2 層のファイルは手順 4 と 5 です。

1. ルール — 解決済みの `aidlc/spaces/<active-space>/memory/` 鎖（最初に載る）
2. 第 1 層の共有方法論 — `.claude/knowledge/aidlc-shared/`
3. 第 1 層のエージェント方法論 — `.claude/knowledge/<agent>-agent/`
4. **第 2 層のチーム共有** — `aidlc/knowledge/aidlc-shared/`
5. **第 2 層のチーム・エージェント固有** — `aidlc/knowledge/<agent>-agent/`
6. 先行ステージの成果物 — いまのステージが消費すると宣言した出力

手順 4 と 5 は、ディレクトリが存在してファイルがあるときだけ発火します。だからチームナレッジが無いプロジェクトは、単に飛ばします。載せはどのステージ開始でも起きるので、ファイルを直すと次の `/aidlc` 実行から効きます。消すキャッシュも再起動もありません。ファイルを外すのも同じです。消せば、以降の実行は見なくなります。同期すべきレジストリはありません。

内面化する帰結が 1 つあります。エージェントはナレッジファイルを **字義どおり、同じ重みで** 読みます。古い、または矛盾するファイルは、積極的にエージェントを誤誘導します。新しいものと同じ権威を持ちます。第 2 層の木は、剪定が要るコードのように扱ってください。レトロでの短い見直しが正直さを保ちます。

手順ごとの契約全体、優先規則、シーケンス図は [Knowledge System → 6-Step Knowledge Loading Order](../reference/10-knowledge-system.md#6-step-knowledge-loading-order) です。

## ナレッジか、ルールか

ハーネスエンジニアがいちばんやりがちな間違いは、意図がルールなのにナレッジに手を出すこと、またはその逆です。互換ではなく、上の載る順がその理由です。ルールは厳格加算の鎖として、実行の前にフレームワークがコンパイルして最初に解決します。ナレッジは、ステージ中にエージェントが秤にかける参照です。

役立つ試験です。**人がレビューするとき、指示に反したらステージ出力を落とすなら、ルールです。** レビューの背景として使うなら、ナレッジです。

| ナレッジに手を出すとき… | ルールに手を出すとき… |
|--------------------------|------------------------|
| エージェントが参照すべき資料を渡している | エージェントが従わなければならない振る舞いの決定を述べている |
| 「これが私たちのパターンです」 | 「X はするな」 / 「いつも Y をしろ」 |
| 中身は情報と文脈 | 中身は規範で交渉不可 |
| 長い散文、表、図でよい | 短く、命令、各 1 行であるべき |
| 例: API Gateway の標準、領域用語集 | 例: 「PII をログするな」、「データアクセスは全部リポジトリ層を通す」 |

だから、チームが API をどう設計するかを述べる文書はナレッジです。`aidlc/knowledge/aidlc-architect-agent/` に置きます。「どのアーキテクチャ判断も代替を少なくとも 2 つ残せ」のような交渉不可はルールです。スペースメモリ層（`aidlc/spaces/<active-space>/memory/`）に置き、フレームワークがエージェントをそこに留めます。層の鎖にルールを書き、ラーニングループが訂正を昇格させるのは [ルールとラーニングループ](05-rules-and-the-loop.md) です。User Guide の [Knowledge vs Rules table](../guide/08-knowledge.md) は、同じ判断をより多くの例で扱います。

## 第 2 層の木の出自

チームが作ります。最初の `/aidlc` で、エンジンは空ディレクトリ 1 つ（`aidlc/knowledge/`）を作り、そこで止まります。木の足場は作らず、エージェントごとのサブディレクトリも、README の種まきもしません。第 2 層の配置（`aidlc-shared/` とエージェントごとのディレクトリ 1 つ）は、ペルソナが見る約束であり、エンジンが書く構造ではありません。中身があるディレクトリを自分で作ります。ローダーは各エージェント自身のディレクトリを名前で歩くので、ローダーが期待する正確な slug で作ってください（`architect/` ではなく `aidlc-architect-agent/`）。誤字の名前はエラーなしで黙って飛ばされます。

ディレクトリ内に命名規則はありません。どの `.md` も載ります。説明的で、ファイルごとに話題 1 つ（`architecture.md` ではなく `api-gateway-standards.md`）はローダーの必須ではありませんが、四半期の剪定がずっと楽です。ディレクトリの出発 README が欲しいなら、第 1 層が任意テンプレートを同梱するので、手でコピーできます。[Knowledge System → Template System](../reference/10-knowledge-system.md#template-system)。

このガイドの残りとの境界についての注記です。ここで埋めるエージェントディレクトリは、エージェントがペルソナファイルで宣言するものと同じです。[エージェントを足す](03-adding-an-agent.md) とき、その第 2 層ナレッジディレクトリは `aidlc/knowledge/<new-agent-slug>/` です。チームが作るディレクトリで、同じ手順 4 と 5 で載ります。[概観](00-overview.md) の頭の模型が持ちます。ステージがエージェントを指名し、エージェントがナレッジを読み、全部データ編集で形を作り、コードは書きません。

## スペース: 複数チームのナレッジ

上はチーム 1 つの前提です。**複数チームが 1 プロジェクトを共有する** とき、AI-DLC は各チームの方法、ナレッジ、記録をそれぞれの **スペース** に保ちます。同じ形の `aidlc/spaces/<name>/`（`memory/`、`knowledge/`、`codekb/`、`intents/`）。この章で使ってきた `aidlc/knowledge/` の略は、本当は `aidlc/spaces/<active-space>/knowledge/` です。チームが 1 つなら、アクティブスペースはいつも `default` で、区別は表面化しません。（[User Guide の Spaces and Intents 章](../guide/03-spaces-and-intents.md) が利用者向けの向きです。この節はハーネスエンジニアリングの角度です。）

書くナレッジとルールへの意味です。

- **チームナレッジはスペース単位です。** 埋める `aidlc/knowledge/aidlc-<agent>-agent/` ファイルは 1 スペースの中にあります。2 つ目のチームは、埋める自分の空の `knowledge/` 木を得ます。あなたのファイルは境界を漏れず、向こうのファイルはあなたのエージェントの文脈を薄めません。
- **方法層もスペース単位です。** `aidlc/spaces/<active-space>/memory/` のルール（`org.md` → `team.md` → `project.md`）は、アクティブスペースの中で解決します。新しいスペースはフレームワークの基線から種まきされます。`org.md` をコピーし、空の新しい `team.md` / `project.md`。新しいチームはフレームワークの既定から始まり、別チームのプラクティスを継がず、自分のプラクティスを稼ぎます。
- **スペースは `core/` に書きません。** スペースは実行時のチームデータで、インストール済みプロジェクトで `/aidlc space create <name>` により作ります。チームナレッジをフレームワークソースから分ける、同じデータ対コードの線です。複数チームを支えるために `core/` に足すものも、再生成するものもありません。能力はエンジンに同梱です。

この章の頭の模型は、各スペースの中で変わりません。ステージがエージェントを指名し、エージェントがナレッジを読み、全部データ編集で形を作ります。スペースは単に *誰の* データを範囲するので、2 チームが 1 プロジェクトで AI-DLC を走らせても、文脈、プラクティス、記録は衝突しません。
