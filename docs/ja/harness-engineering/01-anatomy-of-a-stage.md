# ステージの構造

ステージは AI-DLC ワークフローの原子です。1 ステップで *何が* 起きるか。ハーネスエンジニアがするほかの変更は全部、ステージファイルの上に乗ります。だから最初に読む章です。終わりまでに、どのステージ `.md` を開いても、誰がどの部分を読むか分かり、ファイルを直して変えられるフィールドと、フレームワークのコードが固定する振る舞いを区別できるようになります。

ステージファイルは YAML frontmatter 付きの Markdown 1 枚です。frontmatter はグラフのノードを宣言します。消費する成果物と出す成果物、リードするエージェント、実行の仕方。本文はエージェントが従う散文です。両方を 1 ファイルに置くのは意図的で、この章の残りがその理由をほどきます。

---

## 読者は 2 人、ファイルは 1 枚

ステージファイルには読者が 2 人いて、重なりません。

- **パーサ**は YAML frontmatter だけを読みます。構造化したグラフ項目 — 辺、リードエージェント、実行モード — を出し、本文は完全に無視します。
- ステージを実行する **エージェント**は本文だけを読みます。散文の手順に従い、成果物を出し、frontmatter には触れません。

両方を 1 ファイルに置くと、開いたときにグラフの辺と実行手順が並んで見えます。ステージを読むレビュアーは両方を一度に見ます。どの成果物を出すか、*そして* それを出す指示。分ける — グラフ用の YAML と、エージェント用の散文 — とそのインラインの可視性が壊れます。ステージがレビューできる性質そのものです。

この切れ目が、いま何を直しているかを知る鍵です。frontmatter のフィールドを変えると、*グラフ* が変わります（依存の辺、リードするエージェント、実行モード）。本文を変えると、*仕事* が変わります（エージェントが実際にすること）。二つは独立です。

本物のステージは `core/aidlc-common/stages/<phase>/<slug>.md` に書きます。例: `stages/inception/domain-design.md`。この章と並べて開いてください。終わりまでに形は見慣れたものになります。

---

## frontmatter を一目で

frontmatter は YAML キーの平らな塊です。一部は機械的 — `slug`、`phase` — で、隣のステージからコピーします。本当の判断を運ぶのは一握りで、ステージを書く・直す前に理解する価値があります。

| フィールド | 決めること | 判断 |
|------------|------------|------|
| `requires_stage` | 依存と順序の辺 | このステージは本当に他の出力を消費するか、単に後で走ればよいか |
| `consumes` | このステージが読む成果物 | 成果物ごと: `required` か、ブラウンフィールド / グリーンフィールドの `conditional_on` か |
| `produces` | このステージが書く成果物 | ほかのステージが発見する前方の辺です |
| `lead_agent` / `support_agents` | 誰がステージを走らせるか | ペルソナが 1 人所有し、支援者が視点を足す |
| `mode` | 通信トポロジ | `inline`（コンダクターの文脈の声）、`subagent`（ハブアンドスポークの派遣）、`pipeline`（鎖）、`mob`（有界ラウンドのメッシュ） |
| `for_each` | 反復するか | インスタンスごとに一度走らせる成果物を指名 |
| `reviewer` / `review_artifact` | 独立した品質レビュー | レビュアーを宣言するなら、レビューの対象である必須 Markdown 出力を 1 つ指名する（レビュー記録はその成果物に鍵付けされ、ゲートもそれを指名する）。`produces` の並びには頼らない |

いちばん噛む判断についての注:

- **`consumes[].required` はアクティブな計画に範囲し、全体ではありません。** `required: true` は「*この* ワークフローでプロデューサーのステージが走るなら、この消費は満たされなければならない」という意味です。「プロデューサーはいつも走る」ではありません。スコープは意図して上流ステージを飛ばし、平らな全体要求はそのスコープを構造的に無効にします。ステージ本文は入力が無い場合を丁寧に扱います（「if produced」のような散文）。
- **`consumes[].conditional_on` はブラウンフィールド / グリーンフィールドの切れ目を捉えます。** `conditional_on: brownfield` の消費は、ワークフローがブラウンフィールドのときだけ必須です。無条件の消費はフィールドごと省略します。`always` という値はありません。
- **`mode` は通信トポロジ**です。本文が走るあいだ、誰が誰と話すか。`inline` は短いステージをコンダクター自身の文脈で走らせ、支援者は載せる声です。`subagent` はリードを新しい文脈へ委譲し（Construction のコード生成のような長いステージ）、支援者が宣言されていれば互いに盲目のスポークとして派遣します。`pipeline` は宣言順に支援者を鎖にし、それぞれが上流の仕事全部を見ます。`mob` はリードの草稿に対して支援者を並行で走らせ、異議のラウンドは有界です。誰が参加するかは `support_agents`、どう参加するかは `mode`。`pipeline` と `mob` は空でない `support_agents` を要求します。
- **`for_each` は反復の成果物を指名します。** Unit ごとに一度走る 5 つの Construction ステージは `for_each: unit-of-work` を宣言します。ほかのステージはフィールドを省略し、一度走ります。集約はグラフから推論され、宣言しません。
- **`lead_agent` と `support_agents` は `core/agents/*.md` に対して検証されます。** ハードコードした一覧はありません。エージェントを足すのはそのディレクトリにファイルを置くことです（[エージェントを足す](03-adding-an-agent.md)）。

これは向きであり、契約ではありません。型、制約、あとで AI-DLC が足す予約名前空間のフィールドを含む完全なフィールド表は、Developer Reference の [Field reference — when to use](../reference/15-stage-definition.md#field-reference-when-to-use) です。

## 本文の三区画

frontmatter の下、本文は三区画で、いつもこの順です。`## Steps`、`## Sensors`、`## Learn`。`domain-design.md` を見ると三つとも埋まっています。

- **`## Steps`** はエージェントが従う命令の散文です。ペルソナを載せる、先行文脈を読む、質問ファイルを作る、成果物を出す、承認ゲートを出す。ステージの領域仕事がここにあり、*ステージが何をするか* をグラフに触れずに変えるとき、いちばん直す区画です。
- **`## Sensors`** はコンパクトな局所要約です。出力の置き場、frontmatter の `sensors:` 一覧を映す `Imports:` 行、`upstream-coverage` を取り込むときは `consumes:` を映す `Upstream targets:` 行。意図して省略したセンサーや、構造化出力の所有のような、ステージ固有の例外はここに残します。共有の振る舞いは `stage-protocol.md` §14 です。センサーの全体は [センサー](06-sensors.md) です。
- **`## Learn`** は `stage-protocol.md` §13 のラーニングループ契約を指します。仕事中に四見出しの `memory.md` 日記を保ち、人のゲートの前に確めた学びを面に出して残す。ブートストラップの初期化ステージは日記を保ちますが、ゲートに結ぶやりとりは飛ばします。日記はステージの成果物と一緒です。ワークフロー時の学びはステージ本文を書き直しません。

この三区画はあらかじめ宣言されていたので、v0.5.0 の追加 — 埋まった Sensors と Learn の結び — が、本文の再構成を強制せずにきれいに収まりました。本文模型の全体と、各区画に何を入れてよいかは [Three-compartment body model](../reference/15-stage-definition.md#three-compartment-body-model) です。

内面化する価値のある境界が一つあります。ステージファイルはフレームワークの成果物で、形は不変です。本文の `## Steps` / `## Sensors` / `## Learn` 構造は、ワークフローが書き直しません。ワークフロー内で許される唯一の編集は、ラーニングループが frontmatter の `sensors:` 取り込み一覧に新しいセンサー id を足すことです。ステージファイルで変えるほかは全部、ハーネスエンジニアとして意図して変えます。

## グラフから見た consumes と produces

依存グラフはどこにも直接書かれません。全ステージの `consumes` と `produces` 宣言から浮かび上がります。ステージの `produces` 一覧は前方の辺です。ほかのステージが「誰が `scope-document` を出すか？」と聞くと、それを宣言するステージが答えです。ステージの `consumes` 一覧は後方の辺です。それらの成果物があるまで走れません。

`requires_stage` は依存を明示し、純粋な順序も符号化します。役割は二つです。

1. **意味のあるデータ依存** — 「成果物 X を消費する。ステージ Y が出す」ので、Y を `requires_stage` に入れます。
2. **提示順の辺** — 同じフェーズの 2 ステージにデータ依存は無いが、固定の順がある。弱い辺を書いて、計算した表示順が安定するようにします。アルファベットのタイブレークに頼らない。

ステージを書く、または動かすとき、この 3 一覧がワークフローへの配線です。正しくすれば、正しいスコープに、正しい順で、入力が満たされた状態で現れます。まったく新しいステージを結ぶ手順は [ステージを足す](02-adding-a-stage.md) です。

## stage-graph.json はコンパイルされる — 手では直さない

ソースビルドでは、生成された Claude 投影が `dist/claude/.claude/tools/data/stage-graph.json` からグラフを走ります。`dist/` は `bun scripts/package.ts` が実体化する、無視されるローカル出力です。入れた実行時は、同じ相対ファイルを `.claude/tools/data/` の下に持ちます。JSON は **ビルド成果物** であり、ソースファイルではありません。ステージファイル横断の YAML frontmatter が正本です。JSON はそれをコンパイルした結果です。

流れは:

```
edit stage .md YAML  →  compile  →  stage-graph.json  →  runtime reads it
```

どのステージの frontmatter を直したあとも、コンパイルして `stage-graph.json` を再生成し、両方を一緒にコミットします。CI はドリフト検査を走り、JSON が YAML からコンパイルしたものと一致しなければマージを落とします。忘れられた再コンパイルは出荷されず、捕まります。

従う規則: **`stage-graph.json` を手で直さない。** YAML を直し、再コンパイルします。手編集は次のコンパイルで潰されるか、ドリフト検査に捕まります。コンパイルコマンドとドリフトガードは [Authoring flow](../reference/15-stage-definition.md#authoring-flow) です。

## ステージが *含むもの* 対 *すること*

この章はステージファイルが *含むもの* — 形式 — です。実行時にステージが *すること* の相棒契約があります。承認ゲート、質問の流れ、状態のチェックボックス、完了メッセージ。その振る舞い契約は領域に関係なく全ステージで同じで、[Stage Protocol](../reference/04-stage-protocol.md) にあります。ステージ本文が「承認ゲートは stage-protocol.md に従え」と言うとき、それが指す契約です。

頭の中で二つを分けてください。ステージの *定義*（この章、[reference 15](../reference/15-stage-definition.md)）はファイル形式です。ステージの *プロトコル*（[reference 04](../reference/04-stage-protocol.md)）は、どのステージの仕事にも巻く実行時の振る舞いです。直すのは定義です。プロトコルはだいたい触りません。

frontmatter と本文を結ぶ注釈付きの完全な例は [Worked example](../reference/15-stage-definition.md#worked-example) です。
