# ステージの構造

ステージは AI-DLC ワークフローの原子です。1 ステップで *何が* 起きるかです。ハーネスエンジニアがするほかの変更は、すべてステージファイルの上に乗るので、最初に読む章です。終わりまでに、どのステージ `.md` を開いても、誰がどの部分を読むか分かり、ファイルを直して変えられるフィールドと、フレームワークのコードが固定している振る舞いを見分けられるようにします。

ステージファイルは、YAML frontmatter 付きの Markdown 1 本です。frontmatter がグラフのノードを宣言します。ステージが消費・生成する成果物、リードエージェント、実行の仕方。本文はエージェントが従う散文です。両方を 1 ファイルに置くのは意図的で、この章の残りがその理由です。

---

## 読者は 2 人、ファイルは 1 つ

ステージファイルの読者は 2 人で、重なりません。

- **パーサ**は YAML frontmatter だけを読みます。構造化されたグラフ項目（辺、リードエージェント、実行モード）を出し、本文は完全に無視します。
- **エージェント**はステージ実行時に本文だけを読みます。散文の手順に従い、成果物を出し、frontmatter には触れません。

両方を 1 ファイルに置くと、開いたときにグラフの辺と実行手順が並んで見えます。レビューする人は、どの成果物を出すか *と*、それを出す指示を一度に見ます。グラフ用 YAML とエージェント用散文に分けると、このインラインの見通しが壊れます。ステージがレビューできる性質です。

この切れ目が、編集の意味を知る鍵です。frontmatter のフィールドを変えると *グラフ* が変わります（依存の辺、リードするエージェント、実行モード）。本文を変えると *仕事* が変わります（エージェントが実際にすること）。両者は独立です。

実物のステージは `core/aidlc-common/stages/<phase>/<slug>.md` にあります。例: `stages/inception/domain-design.md`。この章と並べて開いてください。終わりまでに形は馴染みます。

---

## frontmatter の見取り

frontmatter は YAML キーの平たいブロックです。機械的なもの（`slug`、`phase`）は隣のステージから写します。本当に判断が要るのは一握りで、ステージを書く・直す前に理解しておく価値があります。

| フィールド | 決めること | 判断 |
|------------|------------|------|
| `requires_stage` | 依存と順序の辺 | 本当に相手の出力を消費するか、単にそのあとで走ればよいか |
| `consumes` | このステージが読む成果物 | 成果物ごとに `required` か、brownfield / greenfield の `conditional_on` か |
| `produces` | このステージが書く成果物 | ほかのステージが見つける前向きの辺 |
| `lead_agent` / `support_agents` | 誰が走るか | ペルソナ 1 体が所有し、支援は視点を足す |
| `mode` | 通信の位相 | `inline`（コンダクターの文脈の声）、`subagent`（ハブ＆スポーク）、`pipeline`（鎖）、`mob`（回数上限のあるメッシュ） |
| `for_each` | 反復するか | インスタンスごとに 1 回走らせる成果物を指名する |
| `reviewer` / `review_artifact` | 独立した品質レビュー | レビュアーを宣言するなら、追記する `## Review` を所有する必須 Markdown 出力を指名する。`produces` の順には頼らない |

いちばん噛みやすい判断の注記です。

- **`consumes[].required` の範囲は、アクティブな計画です。グローバルではありません。** `required: true` は「*この* ワークフローでプロデューサーのステージが走るなら、この消費は満たされなければならない」です。「プロデューサーはいつも走る」ではありません。スコープは意図して上流ステージを飛ばします。フラットなグローバル必須だと、そのスコープが構造的に無効になります。ステージ本文は、入力が無い場合を散文で扱います（「if produced」など）。
- **`consumes[].conditional_on` が brownfield / greenfield の切れ目です。** `conditional_on: brownfield` の消費は、ワークフローが brownfield のときだけ必須です。無条件の消費はフィールドごと省略します。`always` という値はありません。
- **`mode` は通信の位相です。** 本文が走っているあいだ、誰が誰と話すか。`inline` は短いステージをコンダクター自身の文脈で走らせ、支援は載せた声です。`subagent` はリードを新しい文脈へ委譲します（Construction のコード生成のような長いステージ）。支援が宣言されていれば、互いに見えないスポークとして出します。`pipeline` は宣言順に支援を鎖にし、各リンクは上流の仕事を全部見ます。`mob` はリードの下書きに対し、支援全員を並行で走らせ、異議のラウンドは 1 回までです。誰が参加するかは `support_agents`、どう参加するかは `mode` です。`pipeline` と `mob` は空でない `support_agents` が要ります。
- **`for_each` は反復の成果物を指名します。** Unit ごとに 1 回走る Construction の 5 ステージは `for_each: unit-of-work` を宣言します。ほかはフィールドを省略し、1 回だけ走ります。集約はグラフから推論され、宣言しません。
- **`lead_agent` と `support_agents` は `core/agents/*.md` に対して検証します。** ハードコードされた一覧はありません。エージェントを足すとは、そのディレクトリにファイルを置くことです（[エージェントを足す](03-adding-an-agent.md)）。

ここは向きです。契約ではありません。型、制約、あとから AI-DLC が足す予約名前空間まで含めたフィールド表の全体は、Developer Reference の [Field reference — when to use](../reference/15-stage-definition.md#field-reference-when-to-use) です。

## 本文の 3 区画

frontmatter の下、本文はいつもこの順の 3 区画です。`## Steps`、`## Sensors`、`## Learn`。`domain-design.md` を見ると、3 つとも埋まっています。

- **`## Steps`** はエージェントが従う命令の散文です。ペルソナを載せる、先行の文脈を読む、質問ファイルを作る、成果物を出す、承認ゲートを出す。ステージの領域仕事はここにあり、*ステージが何をするか* をグラフに触れずに変えるとき、いちばん直す区画です。
- **`## Sensors`** は短い局所まとめです。出力の置き場所、frontmatter の `sensors:` 一覧を映す `Imports:` 行、`upstream-coverage` を取り込んでいるときの `consumes:` を映す `Upstream targets:` 行。意図して省いたセンサーや、構造化出力の所有など、ステージ固有の例外はここに残します。共有の振る舞いは `stage-protocol.md` §14。センサーの全体は [センサー](06-sensors.md) です。
- **`## Learn`** は `stage-protocol.md` §13 のラーニングループ契約を指します。作業中は 4 見出しの `memory.md` 日記を維持し、人のゲートの前に確認した学びを出して残します。初期化のブートストラップステージは日記は残し、ゲートに紐づくやりとりは飛ばします。日記はステージ成果物と一緒です。ワークフロー時の学びはステージ本文を書き直しません。

この 3 区画は先に宣言してあったので、v0.5.0 の追加（Sensors と Learn の結び）が、本文の組み直しなしで収まりました。本文模型の全体と、各区画に入れてよいものは [Three-compartment body model](../reference/15-stage-definition.md#three-compartment-body-model) です。

内面化しておく境界が 1 つあります。ステージファイルはフレームワークの成果物で、形は不変です。本文の `## Steps` / `## Sensors` / `## Learn` 構造を、ワークフローが書き直すことはありません。ワークフロー内で許される編集は、ラーニングループが frontmatter の `sensors:` 取り込み一覧に新しいセンサー id を追記することだけです。ステージファイルのほかの変更は、ハーネスエンジニアが意図して行います。

## グラフから見た consumes と produces

依存グラフはどこにも直接書いてありません。全ステージの `consumes` と `produces` 宣言から立ちます。ステージの `produces` 一覧が前向きの辺です。「`scope-document` を誰が作るか」と聞かれたら、それを宣言しているステージが答えです。`consumes` 一覧が後ろ向きの辺です。その成果物があるまで走れません。

`requires_stage` は依存を明示し、純粋な順序も載せます。役割は 2 つです。

1. **意味のあるデータ依存** — 「成果物 X を消費する。ステージ Y が作る」ので、Y を `requires_stage` に入れる。
2. **表示順の辺** — 同じフェーズの 2 ステージにデータ依存は無いが、順序は決まっている。弱い辺を書いて、計算された表示順が安定するようにします。アルファベットのタイブレークには頼りません。

ステージを書く・移すとき、ワークフローへ結ぶのはこの 3 つの一覧です。正しければ、正しいスコープに、正しい順で、入力が満たされた状態で現れます。まったく新しいステージを結ぶ手順は [ステージを足す](02-adding-a-stage.md) です。

## stage-graph.json はコンパイル成果物 — 手で直さない

この実装は、グラフを JSON ファイル `dist/claude/.claude/tools/data/stage-graph.json` から走らせます。これは **ビルド成果物** で、ソースではありません。権威はステージファイル横断の YAML frontmatter です。JSON はそれをコンパイルした結果です。

流れは次です。

```
edit stage .md YAML  →  compile  →  stage-graph.json  →  runtime reads it
```

ステージの frontmatter を直したら、コンパイルして `stage-graph.json` を再生成し、両方を一緒にコミットします。CI はドリフト検査を走り、JSON が YAML のコンパイル結果と一致しなければマージを落とします。コンパイル忘れは出荷されません。

従う規則: **`stage-graph.json` を手で直さない。** YAML を直し、再コンパイルします。手編集は次のコンパイルで潰されるか、ドリフト検査に引っかかります。コンパイルコマンドとドリフトガードは [Authoring flow](../reference/15-stage-definition.md#authoring-flow) です。

## ステージが *含むもの* と、ステージが *すること*

この章は、ステージファイルが *含むもの*（形式）です。実行時にステージが *すること* には、別の契約があります。承認ゲート、質問の流れ、状態のチェックボックス、完了メッセージ。領域に関係なく全ステージ共通で、[Stage Protocol](../reference/04-stage-protocol.md) にあります。ステージ本文が「承認ゲートは stage-protocol.md に従え」と言うとき、指しているのはその契約です。

頭の中では分けてください。ステージ *定義*（この章、[reference 15](../reference/15-stage-definition.md)）がファイル形式です。ステージ *プロトコル*（[reference 04](../reference/04-stage-protocol.md)）が、どのステージの仕事にも被さる実行時の振る舞いです。直すのは定義です。プロトコルはだいたい触りません。

frontmatter と本文を結んだ注釈付きの例は [Worked example](../reference/15-stage-definition.md#worked-example) です。
