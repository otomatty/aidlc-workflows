# ルールとラーニングループ

ルールは、チームがどのワークフローにも持ち込む立ち振る舞いです。毎回の実行の冒頭で説明し直す「いつもこうする」。ハーネスエンジニアとしての書き方は 2 つです。ルールファイルを直接直すか、**ラーニングループ** にワークフロー中の訂正を残るルールへ昇格させるか。この章は、User Guide の [Rules and the Learning Loop](../guide/09-rules-and-the-learning-loop.md) の書く側の相棒です。あちらはループを概念で扱い、ANZ 銀行の例を端から端まで歩きます。ここは運用です。何をどのファイルに書くか、ルールを積んだときの厳格加算の振る舞い、一度の直しが立ち振る舞いになるようループを回す仕方です。

ルールは制御ループのフィードフォワード側です。エージェントが仕事の *前に* 読む散文です。[センサー](06-sensors.md) はフィードバック側です。書き込みの *あと* に発火する決定論的な検査です。ルールは相棒のセンサーを指名できます。両半分は対になるよう設計されています。

---

## 5 層と、直すファイル

ルールは `core/memory/` の下の Markdown です（スペースメモリ層の手書きソース）。スコープごとに 1 ファイルです。`scope:` frontmatter フィールドはありません。この実装はファイル名からスコープを導くので、選ぶファイルが *書くスコープ* です。

| 効かせたいルール | 直すファイル | スコープ |
|------------------|--------------|----------|
| 組織のどのプロジェクトにも | `org.md` | org（フレームワーク既定） |
| チームが走らせるどのプロジェクトにも | `team.md` | team |
| この 1 プロジェクトだけ | `project.md` | project |
| あるフェーズの全ステージ | `phases/<phase>.md` | phase |

フェーズファイルは 4 つです。`phases/ideation.md`、`phases/inception.md`、`phases/construction.md`、`phases/operation.md`（initialization はブートストラップ専用で、ルールファイルは同梱しません）。5 層目（ステージ単位ルール `aidlc-stage-<slug>.md`）は将来のリリース用に空けてあります。いまは書けません。

どのファイルに手を出すかは、判断が 2 つです。

- **`org.md` はフレームワーク同梱です。** どのプロジェクトも継ぐ既定を持ちます。トランクベース開発、walking-skeleton 方針、スコープごとのテスト姿勢。上流として扱ってください。ほとんどのハーネスエンジニアは触らず、team か project に書きます。
- **プロジェクトスコープは、残る逸脱用です。何でもではありません。** `project.md` に手を出すのは、*この* プロジェクトがチーム全体のプラクティスから安定して外れるときだけです。チームが squash するところを rebase するモノレポ、テスト下限を飛ばすレガシー。チームが走らせるどのプロジェクトにも効くルールなら `team.md` です。

各ファイルは、話題の見出しの下の平文です。`## Way of Working`、`## Testing Posture`、`## Deployment`、`## Code Style` など。ルールを足すとは、属する見出しの下に箇条を足すことです。ファイル名とスコープの対応表、リゾルバの仕組みは規範の契約です。[Rule System § Filename-derived scope](../reference/08-rule-system.md#filename-derived-scope) と [§ Layout](../reference/08-rule-system.md#layout)。

## 厳格加算: 層は積む。黙って上書きしない

鎖は、どのワークフローの開始時も 5 層で解決されます。

```
org → team → project → phase → stage
```

模型は **厳格加算** です。当たるルールは全部、エージェントのコンテキストに一度に出ます。実行時に落ちたり抑えられたりしません。組織既定、チームプラクティス、プロジェクト固有は連結です。対応するフェーズルールが付くのは、ステージがすでに frontmatter で `phase:` を宣言しているからです（ステージがほかを取り込むのと同じ、引きの書く向き）。解決済みの鎖は、ワークフロー開始時に各ステージノードへ一度焼き込まれます。ランタイムは歩き直しません。[Rule System § Strict-additive runtime model](../reference/08-rule-system.md#strict-additive-runtime-model) と [§ Five-layer inheritance](../reference/08-rule-system.md#five-layer-inheritance) を見てください。

書く側への意味です。`overrides:` ブロックも、設定する `enforcement:` キーワードもありません。狭い層が広い層に静かに勝ちません。代わりに、書いたどの層もエージェントの見え方に同時にあります。書き方が変わります。効かせたいスコープでルールを肯定形で述べ、上の層を抑えるスイッチではなく、積まれることを信じます。

### 衝突は学びが書く前に見る。実行時には解かない

実行時に上書きが無いので、広いスコープのルールと *矛盾する* ルールは、リゾルバがほどけない問題になります。ラーニングループのプロトコルは、選択が決定論的な書き手に届く前に、オーケストレータに見出し単位の LLM 検査を走らせてそれに応えます。team または project スコープの学びをある `## Heading` の下に足すとき、オーケストレータは提案文を `org.md` の同じ見出しと較べます。矛盾を見つけると、org の文を出し、3 つの選択肢を出します。**直す**、**飛ばす**、org ルールの所有者へ **エスカレート**。衝突が無い、または利用者がエスカレートした選択だけが進みます。project 層の書き込みは org だけを見ます。team 対 project の差は正当なプロジェクト固有であり、方針違反ではありません。

決定論的な `aidlc-learnings.ts persist` 書き手は `org.md` を読まず、この比較を独自には強制しません。受け取った選択を受け入れます。検査は監査の助けであり、強制の境界ではありません。もう一つの受理ゲートは practices-discovery ですが、org 衝突検査は走りません。その昇格は、人の肯定で正当化された決定論的な見出し置換です。読み取り専用の `/aidlc --doctor` 行が 2 つ、あとから状態を出します。**rule-drift** 行は、team または project の中身が埋まっている org 見出しと重なる見出しを旗します（人が確かめる候補の矛盾）。ライフサイクルが古いファイルは別に stale-suppressed として報告します。**paired-coverage** 行は、実際に解決するセンサーを指名しているルールの数を報告します。どちらも advisory で、終了コードは変えません。[Rule System § Rule-drift detection](../reference/08-rule-system.md#rule-drift-detection) を見てください。

## ラーニングループを回す

ルールのもう一つの書き方は、ファイルを開かないことです。ワークフロー中にエージェントを直し、ゲートでその直しを確認し、フレームワークが書いてくれます。それがラーニングループです。ほとんどのステージ実行は何も足しません。健全です。ループが発火するのは、ステージ中に残す価値があるときだけです。

仕組みは [User Guide の章](../guide/09-rules-and-the-learning-loop.md) です。ハーネスエンジニアの見え方は、ループが何を出し、どこに着地するかです。

1. **日記はステージ中に記録します。** コンダクター（アクティブなステージを走らせている生きている `/aidlc` セッション）が、観察ログを `<record>/<phase>/<stage>/memory.md` に維持します（インテントのレコードディレクトリ `aidlc/spaces/<space>/intents/<YYMMDD>-<label>/` の下）。項目は 4 見出しです。Interpretations、Deviations、Tradeoffs、Open questions。自動で作られ、維持されます。手で直さないでください。言語モデルが日記を書き、オーケストレータがあとで受理比較をします。候補抽出と最終書き込みは決定論的な道具です。選択と衝突の処分は、ゲートでのあなたの明示の選択です。
2. **ゲートが候補を出します。** 承認ゲートの前に、ラーニングゲートが `memory.md` を読み、空でない日記行をそのまま候補として見せます。加えて、自由文の「次回に足すことは？」チャネルがあり、観察を打ち、4 見出しのどれに属するかを選びます。
3. **残すものを確認し、書きます。** 確認した学びは日付付き項目として着地します。ファイルパスは選びません。見出しが行き先を決めます。

### 残した学びの着地先

確認した学び *は* プラクティスです。practices-discovery が肯定する同じスペースメモリファイル（`aidlc/spaces/<active-space>/memory/team.md` / `memory/project.md`）に着地します。別の `*-learnings.md` 面はありません。ゲートは話題の見出しで振ります。

| ゲートでの見出し | 着地先 | 監査イベント |
|------------------|--------|--------------|
| Interpretation / Deviation / Tradeoff | `aidlc/spaces/<active-space>/memory/project.md`（既定） | `RULE_LEARNED` |
| 同じものをワンクリックで昇格 | `aidlc/spaces/<active-space>/memory/team.md` | `RULE_LEARNED` |
| Open question | 何も着地しない — 調査項目は昇格しない | — |

既定スコープは **project**、いちばん狭いところです。ワンクリックの「team へ昇格」が、このプロジェクトを超えて効く学びを `memory/team.md` へ広げます。org へ広げる道はありません。org プラクティスはフレームワーク同梱か、別プロセスで組織が書くので、ループは org スコープには書きません。既定を狭く保つことで、1 プロジェクトの驚きが組織全体のルールになる事故を止めます。ラーニングループと practices-discovery は、同じファイルに別のライフサイクルで書きます。ループは日付付き項目を 1 つずつ追記し、practices-discovery は見出し全体を肯定します。リゾルバはファイルを、きれいな整数鎖 org → team → project → phase で並べます。

### 学びがルールではなく検査のとき（`SENSOR_PROPOSED`）

残す価値があるものが *繰り返す手検査* のこともあります。ステージの出力を、同じ欠けに対して何度も目で見る。その種の学びをゲートで確認すると、フレームワークはルールではなくセンサーの結びとして扱います。2 書き込みのインストールを原子的にします。`.claude/sensors/` の下にセンサーマニフェストの足場を作り、発生元ステージの `sensors:` 取り込み一覧に新しいセンサーの id を追記し、`SENSOR_PROPOSED` 監査行を残します。フレームワークのリリース以外でステージファイルに許される編集はこれだけです。取り込み一覧だけが増え、ステージ本文は触れません。そこからマニフェストは手で肉付けします。[センサー](06-sensors.md) です。ループが結びの足場を作り、検査を書くのはあなたです。

### 学びが効くのは次のワークフロー。進行中のものではない

ゲートで捉えた学びは、いまの実行の残りのルールを **変えません**。このワークフローでは、すでに会話でエージェントを直しています。ルールは次回用です。新しい行はディスクにありますが、進行中のワークフローは開始時にコンパイルした見え方を保ちます。次の `/aidlc` が再コンパイルし、ディレクトリ歩きが新しいファイルを拾い、ルールはステージ 1 から効きます。

手で書くときも同じです。ワークフロー途中の `team.md` 編集は、進行中の実行を遡って変えません。ルールが効くのは次のコンパイル境界です。すぐに噛ませたいなら、ワークフローを終えるかやり直して、コンパイルが編集を読み直すようにします。
