# ルールとラーニングループ

ルールは、チームがどのワークフローにも運ぶ立ち振る舞いの判断です。毎回の実行の始めに説明し直す「いつもこうする」。ハーネスエンジニアとして書く方法は 2 つです。ルールファイルを直接直すか、**ラーニングループ** にワークフロー内の訂正を残るルールへ昇格させるか。この章は User Guide の [Rules and the Learning Loop](../guide/09-rules-and-the-learning-loop.md) の書く側の相棒です。あちらはループを概念としてカバーし、ANZ 銀行の例を端から端まで歩きます。ここでは運用です。何にどのファイルを直すか、ルールを積むときの厳格加算模型の振る舞い、一度きりの修正が立ち振る舞いのルールになるようにループを走らせる仕方。

ルールは制御ループのフィードフォワード側です。エージェントが仕事の *前に* 読む散文。[センサー](06-sensors.md) はフィードバック側です。書き込みの *あと* に発火する決定論的な検査。ルールは相棒としてセンサーを指名できます。二つの半分は対になるよう設計されています。

---

## 五層と、直すファイル

ルールは `core/memory/` の下の Markdown ファイルとして住みます（スペースメモリ層の書いたソース）。スコープごとに 1 ファイルです。`scope:` frontmatter フィールドはありません。この実装はファイル名からスコープを導くので、選ぶファイルが *書くスコープ* です。

| 欲しいルールの適用先 | 直すファイル | スコープ |
|---|---|---|
| 組織のどのプロジェクトにも | `org.md` | org（フレームワーク既定） |
| チームが走るどのプロジェクトにも | `team.md` | team |
| この 1 プロジェクト | `project.md` | project |
| 1 フェーズのどのステージにも | `phases/<phase>.md` | phase |

フェーズファイル 4 つは `phases/ideation.md`、`phases/inception.md`、`phases/construction.md`、`phases/operation.md` です（initialization はブートストラップ専用で、ルールファイルを同梱しません）。第五層 — ステージごとのルール（`aidlc-stage-<slug>.md`）— は将来のリリース向けに予約されています。まだ書けません。

どのファイルへ手を伸ばすかを駆動する判断は 2 つです。

- **`org.md` はフレームワーク同梱です。** どのプロジェクトも継ぐ既定を運びます。トランクベース開発、walking-skeleton 方針、スコープごとのテスト姿勢。上流として扱ってください。たいていのハーネスエンジニアは触らず、チームまたはプロジェクトで書きます。
- **プロジェクトスコープは残る逸脱向けであり、全部向けではありません。** `project.md` へ手を伸ばすのは、*この* プロジェクトがチーム全体のプラクティスから安定して外れるときだけです。チームがスカッシュするところでリベースするモノレポ、テストの床を飛ばすレガシープロジェクト。チームが走るどのプロジェクトにも役立つルールなら、`team.md` です。

各ファイルは話題見出しの下の平らな散文です。`## Way of Working`、`## Testing Posture`、`## Deployment`、`## Code Style` など。ルールを足すには、属する見出しの下に箇条を足します。ファイル名対スコープの表全体とリゾルバの仕組みが規範契約です。[Rule System § Filename-derived scope](../reference/08-rule-system.md#filename-derived-scope) と [§ Layout](../reference/08-rule-system.md#layout)。

### リポジトリ全体の Change Control を持つ

これらのファイルの見出し 1 つは、散文ではなく構造設定として読まれます。`## Change Control`。人が承認または確めたあとに入力が変わったときの振る舞いを決めます（ソースが動いた計画、レビューのあと直したレビュー済み文書、現行の要約確認無しで保存した出力）。`strict` はその承認を開き直します。`relaxed` は変更を一度記録し、人に一行で伝え、続けます。既定では各インテントがスコープの値を取り、インテント上の誰でもチャットまたは `/aidlc --change-control <value>` で切り替えられます。全員に `strict` を持たせるには、`team.md`（または `org.md`、1 プロジェクトなら `project.md`）の見出しの下に一行置きます。

```markdown
## Change Control

Mode: strict
```

どの層の `Mode: strict` もスコープ既定とインテント自身の行に勝ちます。relaxed へのチャットまたはフラグの切り替えはそのとき、このファイルを指名する文で拒まれます。走っているインテントの次の統治検査は、ソースとしてファイルを指名する `CHANGE_CONTROL_SET` 行として変更を記録します。ここの `Mode: relaxed` は効果がありません（インテントはいつもスコープまたはチャットで relaxed にできます）。節を空にするのも同じです。ほかの値はファイルと許される 2 値を指名する検証エラーです。行は `## Testing Posture` と同じ `Field: value` 文法で読まれ、コメントアウトした行も含みます。HTML コメントの中の `Mode:` は何も宣言しません。

## 厳格加算: 層は積み、黙って上書きしない

チェーンはどのワークフローの始めにも五層を解決します。

```
org → team → project → phase → stage
```

模型は **厳格加算** です。適用できるルールは全部、エージェントの文脈に一度に現れます。実行時に落ちるものも抑えられるものもありません。org 既定、チームのプラクティス、プロジェクトの特殊化が連結します。一致するフェーズルールが付くのは、ステージがすでに frontmatter で `phase:` を宣言しているからです（ステージがほかの全部を取り込むのと同じ引きの執筆の向き）。解決したチェーンは、ワークフロー開始時に一度、各ステージノードへ焼き込まれます。実行時は再歩きしません。[Rule System § Strict-additive runtime model](../reference/08-rule-system.md#strict-additive-runtime-model) と [§ Five-layer inheritance](../reference/08-rule-system.md#five-layer-inheritance) です。

著者としての意味: `overrides:` ブロックも設定する `enforcement:` キーワードもありません。狭い層が広い層に静かに勝つことはありません。代わりに、書くどの層もエージェントの視界に同時にあります。それが書き方を変えます。適用すべきスコープでルールを肯定的に述べ、上の層を抑えるスイッチへ手を伸ばさず、上の層と積むことを信じます。

### 衝突はラーニングが書く前に検査され、実行時には解決されない

実行時に何も上書きしないので、より広いスコープのルールと *矛盾する* ルールは、リゾルバがほどけない問題になります。ラーニングループのプロトコルは、選択が決定論のライターへ届く前に、オーケストレータに見出し単位の LLM 検査を走らせることでそれに応えます。チームまたはプロジェクトスコープの学びが所与の `## Heading` の下に足されるとき、オーケストレータは提案テキストを `org.md` の同じ見出しと比べます。矛盾を見つけると、org の文を面に出し、三択を出します。**直す**、**飛ばす**、または org ルールの所有者へ **エスカレート**。衝突が無い、または利用者がエスカレートした選択だけが進みます。プロジェクト層の書き込みは org に対してだけ検査します。チーム対プロジェクトの差は正当なプロジェクトの特殊化であり、方針違反ではないからです。

決定論の `aidlc-learnings.ts persist` ライターは `org.md` を読まず、この比較を独立して強制しません。受け取った選択を受け入れます。検査は監査の助けであり、強制の境界ではありません。プラクティス発見はもう一つの入場ゲートですが、org 衝突検査は走りません。その昇格は、利用者の肯定で正当化された決定論の見出し置換です。読み取り専用の `/aidlc --doctor` 行 2 つが、あとから状態を面に出します。**rule-drift** 行は、チームまたはプロジェクトの中身が埋まった org 見出しと重なる見出しを旗します（人が確かめる候補の矛盾）。ライフサイクルが古いファイルは別に stale-suppressed として報告されます。**paired-coverage** 行は、実際に解決するセンサーを指名するルールの数を報告します。どちらも advisory で、終了コードは変えません。[Rule System § Rule-drift detection](../reference/08-rule-system.md#rule-drift-detection) です。

## ラーニングループを動かす

ルールが書かれるもう一つの仕方は、ファイルを決して開かないことです。ワークフロー中にエージェントを訂正し、ゲートで訂正を確め、フレームワークが書いてくれます。それがラーニングループです。たいていのステージ実行は何も足しません。それは健全です。ループが発火するのは、ステージ中に残す価値があるものがあるときだけです。

仕組みは [User Guide の章](../guide/09-rules-and-the-learning-loop.md) です。ハーネスエンジニアの視界は、ループが何を出し、どこへ着地するかです。

1. **日記はステージ中に記録します。** コンダクター（アクティブなステージを走る生きている `/aidlc` セッション）は、観察ログを `<record>/<phase>/<stage>/memory.md`（インテントのレコードディレクトリ、`aidlc/spaces/<space>/intents/<YYMMDD>-<label>/` の下）に保ちます。見出し 4 つの下に項目があります。Interpretations、Deviations、Tradeoffs、Open questions。自動で作られ、保たれます。手で直さないでください。言語モデルが日記を書き、オーケストレータがあとで入場比較をします。候補抽出と最終書き込みは決定論のツールです。選択と衝突の処分は、ゲートでのあなたの明示した選択です。
2. **ゲートが候補を面に出します。** 承認ゲートの前に、ラーニングゲートが `memory.md` を読み、空でない日記行をそのまま候補として示し、自由文の「次回のために足すことは？」チャネルを付けます。そこで観察を打ち、四見出しのどれに属するか選びます。
3. **残すものを確め、書きます。** 確めた学びは日付付き項目として着地します。ファイルパスは選びません。見出しが行き先を決めます。

### 残した学びが着地する場所

確めた学びは *プラクティス* です。プラクティス発見が肯定する同じスペースメモリファイル（`aidlc/spaces/<active-space>/memory/team.md` / `memory/project.md`）に着地します。別の `*-learnings.md` 面はありません。ゲートは話題見出しで経路を決めます。

| ゲートの見出し | 着地先 | 監査イベント |
|---|---|---|
| Interpretation / Deviation / Tradeoff | `aidlc/spaces/<active-space>/memory/project.md`（既定） | `RULE_LEARNED` |
| 同じ、ワンクリックで昇格 | `aidlc/spaces/<active-space>/memory/team.md` | `RULE_LEARNED` |
| Open question | 無し — 調査項目は昇格しない | — |

既定スコープは **project**、いちばん狭い。ワンクリックの「チームへ昇格」手段は、教訓がこのプロジェクトを超えて効くとき学びを `memory/team.md` へ広げます。org へ広げる道はありません。org プラクティスはフレームワーク同梱、または別プロセスで組織が書くので、ループは org スコープでは決して書きません。既定を狭く保つことで、1 プロジェクトの驚きが事故で組織全体のルールになるのを止めます。ラーニングループとプラクティス発見は、二つの違うライフサイクルで同じファイルへ書きます。ループは日付付き項目を一度に 1 つ足し、プラクティス発見は見出し全体を肯定します。リゾルバはきれいな整数チェーン org → team → project → phase でファイルを並べます。

### 学びがルールではなく検査のとき（`SENSOR_PROPOSED`）

残す価値があるものが *繰り返す手検査* のこともあります。同じ欠けをステージの出力で見続けている。その種の学びをゲートで確めると、フレームワークはルールではなくセンサーの結びとして扱います。二書きの導入を原子的にします。`.claude/sensors/` の下にセンサーマニフェストの足場を作り、新しいセンサーの id を元のステージの `sensors:` 取り込み一覧に足し、`SENSOR_PROPOSED` 監査行を残します。それがフレームワークリリースの外でステージファイルに許される唯一の編集です。取り込み一覧だけが伸びます。ステージ本文は決して触れません。そこから [センサー](06-sensors.md) を使ってマニフェストを手で肉付けします。ループは結びの足場を作り、検査はあなたが書きます。

### 学びは次のワークフローに効き、飛行中のものには効かない

ゲートで捉えた学びは、現行実行の残りのルールを **変えません**。このワークフローでは会話でエージェントをすでに訂正しています。ルールは次回のためです。新しい行はディスクにありますが、飛行中のワークフローは始めたときのコンパイル済み視界を保ちます。次に走る `/aidlc` が再コンパイルし、ディレクトリ歩きが新しいファイルを拾い、ルールはステージ 1 から効きます。

手で書くときも大事です。ワークフローの途中で `team.md` を直しても、進行中の実行を遡って変えません。ルールは次のコンパイル境界で効きます。変更をすぐ効かせる必要があるなら、ワークフローを終えるか再開し、コンパイルが編集を再読むようにしてください。
