# リリースのサプライチェーン

AI-DLC のリリースは `awslabs/aidlc-workflows` で、隔離したワークフロー 2 本が作ります。安定タグ向けが `.github/workflows/release.yml`、予定または手動ディスパッチのプレビュー向けが `.github/workflows/preview-release.yml` です。どちらもリポジトリが渡す `GITHUB_TOKEN` を使います。GitHub App、個人アクセストークン、第二のリポジトリ、リポジトリシークレットは要りません。

## リリーストリガー

厳密な `vX.Y.Z` タグを押すとリリースワークフローが始まります。最初のジョブは、次がすべて成り立たない限りリリースを拒否します:

- イベントの ref が押したタグである
- チェックアウトしたコミットがタグの対象である
- タグ対象が `main` に含まれる
- タグが `v` と `core/tools/aidlc-version.ts` の版を足したものと等しい

機能、修正、文書、リファクタ、テストの PR はリリースメタデータを直しません。リリース準備 PR は、前回リリース以降にマージした利用者に見える変更を要約し、タグを作る前に版、README バッジ、changelog 項目をまとめて直します。ワークフローはソースファイルを直しません。

## ビルドと検証

ワークフローは:

1. すべてのハーネス配布を再生成し、決定論的な出力を検査する
2. プロジェクトのテストスイート、typecheck、lint、ShellCheck、PSScriptAnalyzer を走らせる
3. Linux、macOS、Windows 向けのネイティブバイナリをビルドする
4. ネイティブとインストーラのスモークテストを走らせる
5. `aidlc-runtime-X.Y.Z.tar.gz`、インストーラ、`version.json`、`checksums.txt` を作る
6. ステージしたリリース在庫と checksums を検証する

リリースマニフェストはタグ ref と正確なソースコミットを記録します。ランタイムアーカイブ名はリリース版を含むので、利用者は一致する配布を明示して落とせます。

## Provenance

`publish` ジョブが `id-token: write` と `attestations: write` を受け取るのは、ビルドとライフサイクルのジョブが通ったあとだけです。GitHub がステージした成果物向けにビルド provenance を生成します。出した provenance バンドルは `aidlc-release.intoto.jsonl` として入ります。

プレビューワークフローは `main` を毎日スケジュールし、手動ディスパッチも受けます。公開は両方の引き金を合わせて UTC 日あたり高々 1 回です。予定と手動の実行は `release-preview` ワークフロー並行グループで直列化し、走っている実行はキャンセルしません。あとの実行は毎回リリース一覧を読み直します。プランナーは、その UTC 日ですでにプレビューが公開されていれば `main` が進んでいても飛ばし、ソースコミットが最新の公開済みプレビューから変わっていなくても飛ばします。日次検査は、公開済みプレビューの id に載る日付と、GitHub の `published_at` タイムスタンプ（UTC）の両方を数えるので、夜通しのビルドも公開になった日を消費します。

プランナーは計画時点の UTC 日付と、既存タグまたはリリース記録が占有する id を使って `<x.y.z>-preview.<YYYYMMDD>.<N>` を割り当てます。下書きと孤児タグは日次公開枠を消費しないので、再試行の計画は占有 id を越えて `N` を進められます。このカウンタは再試行を許すものであり、公開の日次複数リリースを許すものではありません。残った `aidlc-staging-*` 下書きは、公開者が次の候補をステージする前に検査して消す必要があります。

プランナーは前回プレビュー以降の変更からノートを描きます。呼び出し可能な CI が、通常のリリースビルド連鎖の前に認可したコミットをゲートします。`AIDLC_BUILD_VERSION` はプレビュー id を投影、バイナリ、`version.json`、版付きランタイムアーカイブへ刻み、ソース木は安定の `x.y.z` 版のままです。プレビュー公開者はステージング下書きを検証し、ソースリポジトリとコミットを記録する注釈付きタグを作り、下書きを `make_latest: false` のプレリリースとして公開します。安定の `latest/download` 発見はそのままです。

安定とプレビューの公開は、それぞれ保護された `release` 環境と無人の `preview` 環境を使います。プレビュー環境は同じ `main` デプロイ方針を保ち、必須レビュアーは無しです。マージ承認と呼び出し可能な CI が、人のゲートと決定論的なゲートです。安定実行は別の並行グループを使います。プレビュー公開は、リポジトリで不変リリースが有効であることも要求します。そのリポジトリ設定が無効なら、プレビューワークフローは高いゲートとビルドジョブの前に落ちます。

互換する GitHub CLI があるとき、インストーラは `checksums.txt` をそのバンドルに対して検証し、検証を次へ結びます:

- `awslabs/aidlc-workflows`
- 安定版なら `.github/workflows/release.yml`、プレビュー版なら `.github/workflows/preview-release.yml`
- 安定リリースなら版タグ、プレビューなら `refs/heads/main`
- `version.json` の正確なソースコミット

GitHub CLI が無い、または古い版でも導入は止まりません。そのモードでは、オンライン輸送は HTTPS のみのまま、ソース身元の検証と SHA-256 検査は必須のままですが、クライアントは Sigstore バンドルを認証しません。

## 公開

最後の `release` ジョブは保護された `release` 環境で走り、`contents: write` を受け取ります。リリースに人の承認が要るときは、その環境に必須レビュアーを設定します。承認のあと、ジョブはアテストした候補を落とし、タグと checksums を再検査し、GitHub Release を作ります:

```bash
gh release create "$RELEASE_TAG" build/release/* \
  --verify-tag \
  --title "AI-DLC ${RELEASE_TAG#v}" \
  --generate-notes
```

ジョブはそれから、局所の成果物名を GitHub Release API が返した成果物名と比べます。欠けた、または余分なアップロードはワークフローを落とします。

それより前のジョブはすべて `contents: read` のままです。保管した資格情報がリリース書き込み権限を受け取ることはなく、環境ゲートの前に公開権限を受け取るジョブもありません。

## リリースの作り方

1. 次を直す PR をマージする:
   - `core/tools/aidlc-version.ts`
   - README の版バッジ
   - 一致する `CHANGELOG.md` 見出し
2. 一致するタグを作って押す:

```bash
git switch main
git pull --ff-only
git tag vX.Y.Z
git push origin vX.Y.Z
```

3. `Release` ワークフローを監視する
4. GitHub Release にバイナリ、インストーラ、`aidlc-runtime-X.Y.Z.tar.gz`、`version.json`、`checksums.txt`、provenance バンドルが入っていることを確認する

リリースが作られる前に公開が落ちたら、落ちたワークフローを再実行します。部分的なリリースがあるときは、再実行の前に検査して消します。公開した成果物を黙って置き換えてはいけません。直しは新しいパッチリリースで行います。
