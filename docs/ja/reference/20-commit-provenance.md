# コミット来歴

> 読者: Tier 2/3（チームで入れる人、フレームワークの貢献者）。

この章は **commit provenance** 系の正本です。任意の git コミットまたは差分範囲から、その変更パスを所有するレビュー済み作業単位への、永続する逆引きです。部品は三つ — **コミットした reviewed-source 証拠**（レビュアーが承認した内容のスナップショット。インテントレコードへ書き、どの clone にも付いて回る）、読み取り専用の解決器 **`aidlc attest resolve`**（帰属、ドリフト分類、述べた信頼の根拠）、**`SOURCE_COMMITTED`** 監査アンカー（**補強だけ** — 解決器は決して読まない。`aidlc attest anchor` が書くか、オプトインのセッション開始スイープが書く）。相互リンクは [State Machine](12-state-machine.md)（`SOURCE_COMMITTED` が加わるイベント分類）、[Hooks and Tools](06-hooks-and-tools.md)（`aidlc-attest.ts` のツール項目）、監査形式レジストリ（`knowledge/aidlc-shared/audit-format.md`）、利用者向けコマンドの通し [Guide: CLI Commands](../guide/12-cli-commands.md)。

---

## 1. 問題

Code Generation はすでに、レビューした各ユニットをレビューした正確なソースへ結んでいます。ユニットごとの `REVIEW_COMPLETED` レシートは、そのユニットが主張したパスとマニフェストバイトの上に `Unit Source Fingerprint` を運びます（[Guide: State and Audit — source-bound review receipts](../guide/10-state-and-audit.md#source-bound-review-receipts)）。欠けていたのは *逆向き* です。あとから着地するコミット — しばしば squash、rebase、無関係な変更との束ね — について、どのレビュー済みユニット（とインテント）が各変更パスを所有するか、コミットした中身はレビューした内容とまだ一致するか。その引きが無いと、コミットの下流 — パイプライン、監査者、リリースノート、一年後に履歴を読む人 — は「ここにあるソース変更はすべてレビュー済みユニットへ辿れるか」に答えられません。

## 2. 脅威モデル

解決が答える問いは日常的に混ざる二つで、区別が設計そのものです:

- **完全性** — *着地したバイトは、あるレシートが承認したバイトと等しいか。* 無条件に、中身だけから答えます。検証はバイトがレシートの `Unit Source Fingerprint` へハッシュすることを要求するので、改ざんはパスを `drifted` / `unverifiable` へ移せるだけで、偽って検証することはできません。
- **真正性** — *そのレシートは、実際に起きたレビューが出したものか。* レコードの形では **答えません**。レシート、マニフェスト、証拠はリポジトリ内の普通のファイルなので、リポジトリへ書ける人ならレシートも書けます — 承認するソースと同じ変更集合の中でも。ディスク上では本物のレビューと区別できません。

だから報告は検査した以上を主張しません。どの報告も `trust{}` オブジェクトを運び、自分の帰属の実際の根拠を四段のはしごで指名します:

| `trust.level` | 意味 | 排除するもの |
|---------------|------|----------------|
| `informational` | レコードを **作業ツリー** から読んだ — 同じコミットの clone が再現しないかもしれない局所診断。問うたリポジトリの中にレコードが証明どおり住めないときだけ到達する（§10）。 | 何も。 |
| `reproducible` | レコードを **git ツリー** から読んだので、同じ `(base, head)` はどの clone でも永遠に同じ解決になる — ただし問うた範囲自身がレコードパスを書く（`trust.selfAttested`）ので、変更が自分を裁くレシートを書いたかもしれない。 | 非決定性。事後のレコード編集は過去の報告を変えられない。 |
| `independent` | 再現可能、**かつ** 依拠したレシートは検査対象の変更から来ていない — 範囲がレコードパスに触れないか、`--record-ref` が変更の書けないレコード源へピンしたか。 | 自己承認。変更は自分の判定を製造できない。 |
| `signed` | 独立、**かつ** 判定が依拠する権限を持つ入力すべてが **署名付き** コミットで着いた — 依拠した各ユニットについて、レシートを運ぶ監査シャード **と** そのレシートの指紋が選ぶ証拠ファイルの両方（git `%G?` が `G` / `U`。生コードは入力ごとに `trust.signatures` に出す。少なくとも一つ存在しなければならない）。 | 匿名のレコード書き。各承認が鍵を指名する。 |

アンカーは二つ — どちらも **検証者** が供給し、変更側は供給しない — が報告をはしごの上へ上げます:

- **`--record-ref <ref>`** はレシート、マニフェスト、証拠を、問うたコミットのツリーではなく `<ref>` のツリーから読みます。検査対象の変更が動かせないものへ向けます: 保護ブランチ、レコード専用 ref、レビュー系が維持するミラー。これが `independent` を意味あるものにし、自分で書いた承認を剥がします — レコードをピンすると、捏造したレシートはレコード源に無く、そのパスは `drifted` または `unattested` と出ます。
- **`--require-trust <level>`** はレベルをゲートにします: 達成したレベルが届かない限り終了 **3**（`--fail-on` と共有）。

**範囲内。** レビュー後の中身ドリフト（`drifted`）。欠けた、一致しない、gitignore だけの証拠（`unverifiable`、フェイルクローズ）。単一の所有者を指名しないレシート順序（`indeterminate`、フェイルクローズ）。署名無しレシートが *署名付き* 証拠を選ぶ（`signed` はレシートも覆うので、レベルは `independent` へ落ちる）。自分の承認レシートを書く変更（`reproducible` で頭打ち、`--record-ref` で消える）。問うたコミットとレコードが食い違うチェックアウト（報告へ影響できない — レコードはツリーから読む、§4）。古い判定を変えるための事後のレコード書き換え（同じ理由で不可能）。

**範囲外。** ピンしたレコード ref へ書ける人、またはレコードコミットの署名を偽造できる人は、解決器が尊ぶレシートを出せます — *誰が承認を書いてよいか* を確立するのはホスティング基盤の仕事（ブランチ保護、必須署名、レビューゲート）であり、このツールの仕事ではありません。起きたが雑だったレビューは、それでもレビューです。解決は、レビューしたユニットが *正しい* ユニットだったかについても何も言いません。

**既定の姿勢。** どちらのアンカーも無しでは、報告は **情報メタデータ** です。完全性については正確、権威については沈黙。**強制の仕組み** になるのは、検証者が信頼の根を指名しレベルを要求したときだけです。その選択は検査を走らせる人のものなので、組み込み方針ではなくフラグです — そして `trust{}` が常に出力に乗るので、保存した報告を、それを出したアンカーより強く読むことはできません。

## 3. 設計制約

残りの設計を形作る制約は三つです。各々がよくある仕組みを排除します:

1. **ほとんどのコミットは手動。** 利用者は普通の `git commit` で、どの機械からでも、いつでもコミットします — 変更を出したセッションのかなりあと、もしばしば。だからフックとセッション時の捕捉は *土台* になれません。セッションで観察したものは、良くて補強です。
2. **指紋だけではユニットを指名しない。** レシートの `Unit Source Fingerprint` は *何を* レビューしたかを証明しますが、裸の clone とコミット範囲から始める検証者は、明示してコミットした帰属構造無しでは、変更パスからそのレシートへ行けません。
3. **コミットメッセージは経路ではない。** チームは自分のコミット形式を所有します。トレーラー、チケット接頭辞、メッセージ慣例は頼れず、決してパースしません。

## 4. 帰属模型

帰属は **コミットした中身の純関数** です。コミットのツリーに加え、インテントレコードの *git ツリー*（監査シャード、ユニットの `source-manifest.json`、下のコミットした証拠）。作業ツリー、局所状態、解決対象以外の ref、フックが発火したこと、環境変数、メッセージ本文には何も依りません。帰結は二つ:

- **どの clone も解決できる。** 検査対象のコミットだけがある裸のチェックアウトは、書いた機械と同じ報告を出します。
- **決定性。** 同じ `(base, head)` 対は常に同じ帰属を出し、何年あとも続きます。もっとユニットをレビューする、レコードを直す、チェックアウトの証拠を編集する、では過去のコミットの解決は遡って変わりません。*除外* も同じです。ハーネスシェルは範囲の base ツリーにあるコミット済み `<dir>/tools/data/harness.json` が確立するので、チェックアウトでハーネスを入れたり外したりしても、過去コミットの `.claude/**` パスを `excluded` と `unattested` のあいだでひっくり返せません。変更が自分の除外を宣言することもできません。

レコード源の既定は問うた head 自身のツリーで、`--record-ref` が上書きします（§2）。ツリーから読むことが上の二つの性質を真にします。作業ツリーを見るのは、レコードが問うたリポジトリに入れない唯一の配置（検査対象リポジトリの外にレコードルートがあるマルチルートワークスペース）だけで、その報告は `informational` であり、そう述べる `warnings[]` 項目を運びます。

所有は完了時にエンジンが使うのと同じレシート意味論に従います。各ユニットについて、**いちばん新しい READY `REVIEW_COMPLETED`** レシート（`Verdict: READY`、`Unit`、`Stage`、`Unit Source Fingerprint` を運ぶもの）が権威です。レシートはタイムスタンプ、それからシャード内位置、それからシャード索引で並べます。同じユニットの READY レシート二つが同じタイムスタンプで *別* シャードにあると順序が付かず、フェイルクローズします（`indeterminate`、§6）。複数ユニットが主張するパスはいちばん新しい主張者のものです — 完了が適用する「新しいレビュー済み主張が、意図した共有ファイル統合を所有できる」と同じ規則 — いちばん新しいタイムスタンプを二人の主張者が共有すると、「いちばん新しい」は単一の所有者を指名しないので、そのパスも名前順では解決せず `indeterminate` でフェイルクローズします。

所有レシートごとに、パス主張は使えるいちばん強い源から、次の順で来ます:

| `claimsSource` | 意味 |
|----------------|------|
| `manifest` | ユニットの `source-manifest.json` が、証拠ヘッダに記録したマニフェストダイジェストへハッシュする — 完全な主張忠実度。ディレクトリ接頭辞主張（`src/generated/`）も含む |
| `evidence-only` | 検証できるマニフェストが無い。主張は証拠一覧の正確なパスキーへ落ちる（接頭辞主張は失われる — 主張したディレクトリの下の新ファイルは `unattested` と出る） |
| `manifest-unverified` | マニフェストはあるが証拠に対して検証できない（例: 証拠が欠けている）。パスはまだ帰属するが、中身は検査できない |

## 5. コミットした reviewed-source 証拠

レビュー時、エンジンはユニットの reviewed-source スナップショットを二重書きします:

- **コミットした証拠**（解決の権威）: インテントレコード内の `<record>/construction/<unit>/<stage>/reviewed-source-<hash12>.tsv`。`<hash12>` は指紋の先頭 12 十六進桁。レコードがコミットされるので、証拠はどの clone にも付いて回ります。
- **局所スナップショット**（既存）: `<record>/.aidlc-source-review/<stage>/unit-<unit>-<hash12>.tsv`。機械局所（無視）。完了時の鮮度検査のために残します。解決の検証源では **ありません**（§6） — gitignore したバイトを尊ぶと、判定がどの機械で走ったかに依ります。

スウォーム worktree の中でレビューしたユニットは、両方のファイルを外へ運びます。最終化がメインレコードへ移す reviewed-record スナップショット（`aidlc-swarm.ts` の `captureReviewedRecordSnapshot` / `mergeReviewedRecordSnapshot`）は、ユニットの `source-manifest.json` **と** `reviewed-source-<hash12>.tsv` を含み、移す前にレシート指紋へハッシュ検査し、レコード成果物と同じ all-or-nothing トランザクションで書きます。コミットした証拠が存在する前にレビューした進行中スウォームでは、最終化がバイト一致でレシート結びの局所スナップショットをそのコミットパスへ昇格します。変えた、または欠けた局所証拠はまだフェイルクローズします。だからスウォームが作ったユニットは、アップグレード後に再レビューせず、インラインと同じく解決します。

両方のファイルは **バイト一致の中身** を持ち、レシートの `Unit Source Fingerprint` は正確にそれらのバイトの SHA-256 です — 第二の指紋スキームはありません。証拠をコミットしても **新しい指紋意味論はゼロ** です。書きは内容アドレスです。同じ指紋の書き換えは冪等な no-op、同じアドレスに違うバイトを見つける書きは拒否します（`address collision or corruption`）。

ファイル形式（`aidlc-lib.ts` の `parseUnitSourceListing` / `serializeSourceListing`）は厳密な TSV 文法です:

```
manifest\t<sha256-of-manifest-bytes>\t-\n
<repo>\t<path>\t<mode>\t<oid>\n        # zero or more rows, sorted by key
```

ヘッダはマニフェストバイトを結びます。各行は主張したパスのリポジトリセレクタ（ワークスペースルートなら空）、パス、git ファイルモード（`/^\d{6}$/`）、blob OID（40–64 hex）を記録します。フィールド内の `\t`、`\n`、`\r`、`\\` はバックスラッシュエスケープします。重複キー、欠けた末尾改行、壊れたフィールドはどれもファイル全体を拒否します（パーサは null を返す → 証拠は無いものとして扱う）。妥当なヘッダのあとの空一覧は妥当です（レビューが生き残るパスを主張しなかったユニット）。

## 6. 解決 — `aidlc attest resolve`

```
aidlc attest resolve [<commit>|--commit <rev>] [--diff <base>..<head>]
                     [--repo <name>] [--space <name>] [--intent <dir>]
                     [--record-ref <ref>] [--require-trust <level>]
                     [--fail-on <statuses>]
```

読み取り専用 — resolve は決して書かず、監査イベントを出さず、`SOURCE_COMMITTED` アンカーを読みません。モード: 単一の `<commit>`（位置または `--commit <rev>`、両方は不可）はそのコミットの first-parent 差分を解決します（既定 `HEAD`）。`--diff <base>..<head>` は範囲端点を直接解決し、三点形 `<base>...<head>` はマージベースを使います。各動詞は自分のフラグだけを受けます — `resolve --reconcile` と `anchor --record-ref` は usage エラー（終了 1）であり、黙って無視しません。親が浅い clone のために欠けているコミットはエラーであり、木全体の差分ではありません（§10）。差分の変更パスすべてを分類します:

| 状態 | 意味 | 落とせる |
|--------|------|:--------:|
| `verified` | レビュー済みユニットが所有し、コミットした blob OID がレビューした証拠と一致する | — |
| `drifted` | レビュー済みユニットが所有するが、コミットした中身がレビューした内容と違う | ✓ |
| `unattested` | レビュー済みユニットがそのパスを主張していない | ✓ |
| `unverifiable` | レシートがパスを主張するが、中身を結ぶコミット済みバイトが無い: レコード源から証拠が欠けている、レシート指紋へハッシュしない、gitignore した局所スナップショットにしか無い — **フェイルクローズ**。黙って検証しない | ✓ |
| `indeterminate` | レシート順序が曖昧 — 同じタイムスタンプの READY レシートが別シャード、またはパスを両方主張する別レコード — **フェイルクローズ** | ✓ |
| `excluded` | フレームワークシェル（リポジトリが運ぶときの `aidlc/` / `.aidlc/`）、インテントレコード下の入れ子 `.aidlc-sensors/` ディレクトリ、および — ワークスペースシェルを運ぶリポジトリでは — 範囲の base ツリーですでに確立したハーネスシェルディレクトリ（`.claude/`、`.kiro/`、…。コミット済み `<dir>/tools/data/harness.json` で識別）。head が導入したマニフェストは自分や兄弟を除外できない — 決して帰属せず、決して落とせない | — |

`--fail-on` は落とせる四状態のカンマ区切り部分集合を取り、一致すると終了 **3**（0 = きれいに解決したか何も一致しなかった、1 = usage / 環境エラー）。`unverifiable` を省くゲートは、レビューした中身を何も検査できなかったパスを通すので、厳しいゲートは四つすべてを指名します。`--require-trust <level>` も、達成した `trust.level` が足りないと終了 3 です（§2）。二つのフラグは直交します — `--fail-on` は *変更のどれだけが attested か* を上限し、`--require-trust` は *報告をどれだけ信頼できるか* を上限します。

報告は stdout の JSON です: `paths[]`（パスごとの状態 / ユニット / インテント / 理由）、`units[]`（所有レシートの詳細 — ステージ、イテレーション、`evidenceSource`、`claimsSource`、記録した迂回、証拠を最後に書いたコミットの `evidenceCommit` / `evidenceSignature`、勝ったレシートを運んだ監査シャードとそのシャードを最後に書いたコミットの `receipt` / `receiptCommit` / `receiptSignature`、`fullyLanded`: 主張したパスすべてが `head` でレビューした OID に着地したか）、状態ごとの `summary` 件数、エコーした `failOn`、`trust{}`（§2 — `level`、`required`、`satisfied`、`recordSource`、`recordRef`、`recordCommit`、`recordPinned`、`recordPathsChangedInRange`、`selfAttested`、`signatures[]`）、`warnings[]`。

`warnings[]` は、どの単一パスの分類も変えずに報告全体を歪めうる条件を指名するので、それだけではゲートを落としません: リポジトリのバイト形変換（`core.autocrlf`、`.gitattributes` — §10）、コミットしたインテントレコードをまったく運ばないレコード源（だから何も帰属できない。そうでないと「何も attested でない」と同一に読める）、作業ツリーレコードへのフォールバック（§4）。

ユニットごとの証拠は検証するために **コミット** されていなければなりません（`evidenceSource: "committed"`）。レガシーの局所スナップショットはまだ見つけ、診断として出します（`evidenceSource: "local"`） — 二重書きが存在する前にこの機械でレビューが起きた、と知らせます — しかしそのバイトはパスを決して検証しません: それらのユニットは `unverifiable` で、証拠をコミットする再レビューを指す理由が付きます。これで、どの機械が問うてもコミットあたり判定は一つです。マルチルートワークスペースは呼び出しあたりリポジトリ一つを解決します: 既定はワークスペースルート、または `--repo <name>` で記録したリポジトリ（プロジェクト dir 自身が git リポジトリでないときは必須）。

## 7. アンカー — `SOURCE_COMMITTED`（補強だけ）

```
aidlc attest anchor [--commit <rev>] [--reconcile] [--max-commits <n>]
                    [--repo <name>] [--space <name>] [--intent <dir>]
```

`anchor` はコミット（既定 `HEAD`）向けに解決を走らせ、レビュー済み主張が着地していれば、関与したインテントごとに `SOURCE_COMMITTED` 監査イベントを追記します — 監査証跡の人が読める前向きポインタ（「このコミットがこれらのユニットを運んだ」）。厳密に **補強** です: resolve はアンカーを決して読まないので、利用者がいつも手動コミットだけで `anchor` を決して走らせないリポジトリは、監査証跡の読みやすさ以外は何も失いません。

フィールド: `Commit`、`Repo`（記録したセレクタ、またはワークスペースルートなら `-`）、`Units`（カンマ区切り、ソート済み）、`Attributed Paths`（件数）、`Observed`（直接呼び出しなら `session`、履歴スイープなら `reconciled`）。意味論:

- **重複排除** — インテントごとに `(commit, repo)`。すでにアンカーしたコミットの再アンカーは重複ではなく skipped と出る。
- **スウォーム認識** — `SWARM_SOURCE_MERGED` イベントの `Merge commit` がすでに結んだコミットは飛ばす（スウォームの審判がより豊かな文脈ですでにアンカーしている）。
- **有界な再構成** — `--reconcile` は直前 `--max-commits` 件の first-parent コミット（既定 100）を、以前のアンカーに構わず歩く — 重複排除はコミットごとなので、すでにアンカーした領域の後ろの未アンカー隙間も埋まる — 各コミットを anchored、skipped、unattributed、または浅い `boundary` として報告する。
- **浅い clone に安全** — 浅い clone の境界コミットは到達できる親が無いので、差分は知り得ない。単一コミットの `anchor` はそれでエラーにする。`--reconcile` は `boundaries[]` に載せて先へ進み、その中でパスを一度でも主張した全ユニットへ木全体を帰属させない。
- **曖昧さは静かに** — 所有が曖昧なパス（§6 の `indeterminate`）はアンカーしない。曖昧さの報告は resolve の仕事。
- **CLI 保護** — `SOURCE_COMMITTED` は `CLI_PROTECTED_EVENT_TYPES`（`aidlc-audit.ts`）に入る: 所有ツールだけがライブラリ経路で追記する。エージェントは監査 CLI 経由で捏造できない。*マージ保護ではない* — シャードマージはほかのイベントと同じく運ぶ。
- **作業ツリーのレコード** — `anchor` は設計どおり作業ツリーからレコードを読む: いまの局所リポジトリを観察し、出力はどの判定も依拠しない補強。§4 のツリー読み決定性が要るのは `resolve` だけ。

アンカーは **既定で明示** です。アンカーは解決が決して読まない補強なので、書くことは運用者が頼む行為です: `aidlc attest anchor [--reconcile]`。コマンドを覚えずに監査証跡へ着地コミットを載せたいチームは、**`AIDLC_SESSION_ANCHOR=1`** をセットしてセッション開始スイープへオプトインできます: セッション開始フック（`hooks/aidlc-session-start.ts`）が、本物のセッション開始で最善努力の `runAnchor` 再構成を 25 コミットに有界して走らせます（人はほとんどセッションとセッションの*あいだ*にコミットするので、次のセッション開始が自然な観察点です）。インテントごとの重複排除で毎セッションの再実行は冪等です。スイープは起動を決して止めず（非 git ワークスペースなどの失敗は飲み込む）、compact 再開と rebind 探りでは飛ばします。スイッチ未設定 — 既定 — では、セッション開始は監査行を書かず、来歴の仕事もしません。新しいチェックアウト、フック無効のハーネス、セッション上限より深い履歴（`--max-commits`、既定 100）をアンカーする道は、明示動詞のままです。

## 8. 保証と端ケース

- **squash / rebase の安定。** 帰属は blob 中身（OID）を鍵にし、コミット祖先ではありません — ほかと squash して着地したレビュー済み変更はまだ検証し、revert したファイルをレビューしたバイトへ戻して再着地すると `verified` に戻ります。
- **アップグレード前のレコード。** 証拠の二重書きより前にレビューしたレコードはコミットした証拠が無く、どこでも `unverifiable` です — 書いた機械でも裸の clone でも同じ — 次のユニットごとのレビューが証拠を二重書きするまで。フェイルクローズし、理由は欠けているものを述べます。
- **除外実装は一つ。** 任意コミットの一覧は `gitCommitSourceListing`（`aidlc-lib.ts` から export）から来るので、コミット側とレビュー側はドリフトする二コピーではなく単一の除外実装を共有します。ハーネスシェル規則（`isHarnessShellManifest`）も同じく関数一つで、ここではツリー blob に、レビュー時はディスク上のファイルに当たります。バイト形の意味論は **共有しません** — §10。
- **改ざんの非対称。** 検証はレシートの `Unit Source Fingerprint` へハッシュするバイトを要求するので、証拠を壊すとパスを *落とす*（`unverifiable`）だけで、偽って検証はできません。コミットした証拠の破壊は、無傷の局所コピーでは隠れません。局所バイトは検証しないからです。*チェックアウト* で壊しても無効です: 勘定するバイトはレコードツリーの blob です。
- **レコード読みは git 呼び出し一対。** ツリー裏のレコードビューはレコード部分木を一度一覧し（`git ls-tree -r -z --full-tree`）、要る blob すべてを単一の `git cat-file --batch` でまとめます。履歴からレコードを読むコストは、ディスクから読むのと同程度です。

## 9. 信頼の組み方

ほとんどのチームは二つの形で足ります:

- **保護ブランチ上のレコード。** レビュー系は、自分だけが動かせる ref へレコードコミットを押します（`refs/heads/aidlc-records`、またはミラー）。検証者は `resolve --diff <base>..<head> --record-ref aidlc-records --require-trust independent --fail-on drifted,unattested,unverifiable,indeterminate` を走らせます。自分のレシートを書く変更は何も得ません: そのレシートはピンしたツリーにありません。
- **変更と並ぶレコード、署名付き。** レコードは同じリポジトリに住み変更と着地しますが、レコードコミットは署名され、ブランチは署名を要求します。`--require-trust signed` は、依拠した入力すべて — レシートシャードも証拠ファイルも — が署名付きコミットで着いたときだけ持ちます。署名できる変更著者はまだ自己承認できる、という注記 — 署名は鍵を指名し、役割は分けない — なので、この形は帰属と否認防止向き、ピンした ref の形は職務分離向きです。両方にするなら組み合わせます。

どちらのアンカーも無しで走らせるのは正当な第三の形です: そのとき `resolve` は、何が着地したか、レビューと一致するかを教える報告ツールであり、`trust.level` がその限界を正確に文書化します。

## 10. 限界

- **信頼の根はここでは確立しない。** `resolve` は読んだレコードの来歴を報告します（`trust{}`）。ref を信頼できるものにするのは、ホスティング基盤のブランチ保護、署名方針、アクセス制御です（§2、範囲外）。
- **署名はコミット単位。** 権限を持つ各ファイルを最後に書いたコミットの `%G?` — レシートの監査シャードと、それが選ぶ証拠ファイル — がいちばん強い使える信号です。承認ごとの署名は無く、*どの* 身元が承認してよいかという概念もありません。git が受け付けるどの鍵からの妥当な署名（`G`、または信頼しない鍵からの妥当な署名なら `U`）も署名済みと数えます。キーリングを設定し、区別が大事なときは `trust.signatures[]` を読んでください。
- 解決は *着地した中身* を *レビューした中身* に対して分類します。ドリフトしたパスのレビュー対実際の **差分** は、レビューした blob が到達できないと出せません（証拠は OID を記録し、ファイル本文ではない）。差分が欲しいチームは、レビューした blob を生かしておく ref を押すか、帯域外に保管しなければなりません。
- 呼び出しあたりリポジトリ一つ。ワークスペース横断の報告は `--repo` セレクタのループです。
- `--fail-on` はパス状態だけをゲートします。「`docs/` の下なら `unattested` でよい」のような方針は、ツールの中ではなく、終了コードの周りのパイプラインに属します。
- **作業ツリー対リポジトリのバイト形。** レビュー証拠は作業ツリーバイトをハッシュします（`stableFileSha256`）。コミット側の一覧は、チェックアウトフィルタを意図して無効にした生のリポジトリ blob を読みます。clean / smudge フィルタ、`core.autocrlf`、作業ツリーの符号化が効いているところ — Git LFS、または既定 `autocrlf=true` の Windows チェックアウト — では、両側が同じ中身を違うハッシュにし、変わっていないパスが `drifted` と出ます。サブモジュール gitlink（モード `160000`）は一覧項目がまったくありません。`resolve` は検出できる原因を `warnings[]` に印します。それらの機能を使うリポジトリは、ゲートが使える前にバイト形を揃える必要があります。揃えると指紋入力が変わるので、別変更です（`docs/roadmap.md`）。
- **浅い clone。** `resolve <commit>` と単一コミットの `anchor` は、浅い境界コミットを実行可能なエラーで拒否します（clone を深くする。パイプラインでは `fetch-depth: 0`）。ルートツリーに対して差分してチェックアウト全体を分類しません。`anchor --reconcile` はそうしたコミットを `boundaries[]` に記録します。`--diff` で解決する範囲は、両方の端点とそのマージベースが必要です。
- **問うたリポジトリの外のレコード。** レコードルートが検査対象リポジトリの中に無いマルチルートワークスペースでは、そのリポジトリのどのツリーもレコードを含まないので、作業ツリーが唯一使える源です: 報告は `informational` で警告を運び、`--record-ref` は黙って無視せず、尊べないものとして拒否します。
