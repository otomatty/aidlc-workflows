# プレーンアーキテクチャ

> 読者: Tier 2/3（チームで入れる人、フレームワークの貢献者）。

この章は、AI-DLC の三プレーン — コントロール、データ、マネジメントの関心の分離 — と、それらをつなぐコンパイル境界です。相互リンクは [Sensor System](07-sensor-system.md)（コントロールプレーンのセンサーマニフェスト）、[Rule System](08-rule-system.md)（コントロールプレーンのルールファイル）、[State Machine](12-state-machine.md)（データプレーンのライフサイクル）です。ここは設計の土台です。センサーとルールのマニフェストは、土台が扱うソースファイルです。

---

## 1. 問題

v0.5.0 はルール、センサー、ラーニングループを入れます。ワークフロー実行中の観察をどこかに書き、次から自動で発火するようにします。下のモデルは本当に複雑です。複数種のステージ単位 import、ファイル名で付く万能既定ルール、センサーマニフェスト、フック連鎖。利用者は全部を覚えなくてもフレームワークを使えなければならず、フレームワークもホットパスで検索代を払ってはいけません。

正しい枠は「設計を単純にする」ではありません。*「すでにこういう系にある規律を借りる」*です。現代ネットワーキングの三プレーンが一番近く、教訓はほぼそのまま移せます。

---

## 2. ネットワーキングの類比

現代のルータ（または SDN コントローラ）は仕事を三プレーンに分けます。

- **マネジメントプレーン** — SNMP、syslog、ダッシュボード、NETCONF、gRPC、CLI。設定が入り、観測が出る。人の速さ（一度設定し、たまに照会する）。
- **コントロールプレーン** — BGP、OSPF、IS-IS、経路計算。トポロジが与えられたら、各パケットがどの道を行くかを決める。トポロジの速さ（秒から分）。
- **データプレーン** — フローテーブル、ACL、ASIC 転送。このパケットを今、ナノ秒で、テーブル参照で転送する。回線速度。

盗む価値のある教訓は五つです。

### フィルタ評価はパケット速度ではしない

OSPF はトポロジが変わったとき一度だけ最短路を計算し、結果をデータプレーンのフローテーブルへ入れます。以後のパケットはテーブル参照です。ナノ秒、決定論、フィルタ論理なし。賢い仕事は*トポロジ変更時*であり、*パケット時*ではありません。

### プレーン間のインタフェースは明示する

OpenFlow、P4、NETCONF、gRPC。コントロールプレーンはデータプレーンのメモリに手を入れません。「このフローを入れろ」という構造化メッセージを送り、データプレーンが確認します。失敗の型が診断できます。拒否された install ははっきりした合図であり、静かな見逃しではありません。

### 失敗はきれいに隔離する

コントロールプレーンが落ちても、データプレーンは最後に入れた規則で転送を続けます。データプレーンが落ちたら、コントロールプレーンはハートビートで気づき、障害を迂回します。片方をもう片方が落とさないことは、負荷を支える性質です。

### テレメトリがループを閉じる

データプレーンはフロー統計、ドロップ、遅延を報告します。コントロールプレーンはテレメトリを消費し、混雑の迂回、サービスの拡大、ピアの down を決めます。*コントロールプレーンが賢くなるのは、データプレーンが報告するからです。*

### 三プレーン、三つの速さ

マネジメントプレーンは人の速さ。コントロールプレーンはトポロジの速さ。データプレーンは回線速度。仕事が許せば、各プレーンは遅くてよいです。

## 3. AI-DLC への写し

写しは見かけより近いです。（以下の `<record>/` はアクティブインテントのレコードディレクトリ、`aidlc/spaces/<space>/intents/<YYMMDD>-<label>/`。監査証跡は `<record>/audit/` のクローンごとのシャードです。）

| ネットワーキング | AI-DLC の対応 |
|---|---|
| コントロールプレーン（BGP、OSPF、経路計算） | ステージ定義、ルール、センサー — 何が走るべきかのスキーマ |
| データプレーン（パケット転送、フローテーブル） | ステージ実行、ボルト、エージェント呼び出し — 実際の実行 |
| マネジメントプレーン（SNMP、ダッシュボード、CLI） | `/aidlc --doctor`、designer（将来）、監査照会、`CLAUDE.md` |
| ルーティングプロトコル（BGP / OSPF） | コンパイル: `aidlc-graph.ts compile` がステージ frontmatter + ルール + センサーを読み、各ステージの pull import をソースレジストリに解決し、グラフを出す |
| ASIC に載った FIB（転送情報ベース） | コンパイル時に解決済みの、ステージごとの `rules_in_context` + `sensors_applicable` を持つ `stage-graph.json` |
| OpenFlow / NETCONF（インタフェース） | `stage-graph.json` — コンパイルとオーケストレータの明示インタフェース |
| テレメトリ（NetFlow、sFlow） | 監査ログ、センサー発火、memory.md の記録 → インテントの `runtime-graph.json` |
| 反応的なフロー投入（PACKET_IN） | ラーニングループ: データプレーンが観察を報告 → 人が確認 → ルール / センサーへのファイル書きと、新しいセンサー結びを取ったとき発信ステージの frontmatter 編集 |
| 先行的な経路投入（BGP 広告） | フレームワーク PR: どのワークフローも走る前に新しいステージ / ルール / センサーを出荷する |
| トポロジ変更 → 経路の再計算 | ワークフロー開始 → コンパイルがいまのソースを読む。以後の再計算は次のワークフローが引き金 |
| パケット飛行中も安定な、事前投入 FIB | ワークフロー中のラーニングループ書き込みは、飛行中のコンパイル済みビューを変えない。次のワークフロー開始から効く（§5） |
| テーブル参照による回線速度転送 | オーケストレータとディスパッチャが、グラフノードの事前解決フィールドを読む。実行時の解決歩きはしない |

`stage-graph.json` のプレーンラベルと実行時の読み方は、FIB / 経路表 / CLI の分離を映します。設定はマネジメントプレーンから入り、コントロールプレーンがコンパイルし、データプレーンは参照で実行します。

## 4. コンパイル境界

支える洞察です。ネットワーキングがフィルタ評価や継承歩きをパケット速度に置かないのは、そこでは高すぎるからです。コントロールプレーンが一度計算し、FIB に入れ、データプレーンは参照で転送します。AI-DLC も同じです。ワークフロー開始で一度コンパイルし、ワークフロー中は解決済みビューを読み、次のワークフロー開始で再コンパイルします。

### 何がコンパイルされ、何がディスクに残るか

| 状態 | 寿命 | ディスク上のソース | コンパイル先 | 読むもの |
|---|---|---|---|---|
| ステージ DAG、スコープルーティング、成果物生成 | フレームワーク版（フレームワーク PR で変わる） | ステージ frontmatter（`.claude/aidlc-common/stages/*.md`） | `stage-graph.json` | オーケストレータ、doctor、designer |
| **ルール**（散文、規定） | 可変。フレームワーク PR かラーニングループの書き込み | `aidlc/spaces/<active-space>/memory/<scope>.md`（ファイル名から導出。org / team / project は全ステージに付く） | `stage-graph.json` のノードごとの `rules_in_context` | オーケストレータ（解決済みビュー）。Claude Code の自動読み込みはソースを読んで文脈の散文にする |
| **センサー**（マニフェスト、検証検査） | 可変。フレームワーク PR かラーニングループの書き込み（マニフェストは一度書き、ステージは id で import） | `.claude/sensors/aidlc-<id>.md` | `stage-graph.json` のノードごとの `sensors_applicable` | ディスパッチャがステージ入場で解決済み一覧を読む。PostToolUse がそこから発火 |
| ワークフロー実行のテレメトリ | ワークフローごと、蓄積 | `audit/` シャード · `memory.md` · ボルト分岐 | `<record>/runtime-graph.json` | doctor、ゲートの儀式、将来のワークフロー横断オブザーバ |
| ステージごとの観察ログ | ステージ実行ごと | `<record>/<phase>/<stage>/memory.md` | （コンパイルしない — 直接読む） | そのステージのゲートでの儀式 |

コンパイル成果物は二つで、どちらもワークフローごとです。`stage-graph.json` は解決済みコントロールプレーンビューです。ステージ DAG、スコープルーティング、成果物生成、それに継承を事前解決したステージごとのルールとセンサー一覧。`runtime-graph.json` は再コンパイルします — 遷移クラスの監査イベントのたびに、監査ログのイベントソース歩きです。ディスク上のソースは書く面です。実行時が読むのはコンパイル済みグラフです。

### コンパイルはワークフロー開始で一度

コンパイルはステージ frontmatter を読み、`aidlc/spaces/<active-space>/memory/` と `.claude/sensors/` を歩き、ファイル名で万能既定ルールを付け（`org.md`、`team.md`、`project.md` は全ステージに効く）、各ステージの pull import をソースレジストリに引きます。

- ステージの `phase: <name>` が、対応する `phases/<name>.md` ルールを付ける（ステージにつきルール一つ）。[Rule System](08-rule-system.md) を見てください。
- ステージの `sensors: [<id>, ...]` が一覧の各 id を `.claude/sensors/` に解決します。未知の id はコンパイルを騒がしく落とします。import したものが静かに発火しない、は許しません。[Sensor System](07-sensor-system.md) を見てください。

コンパイルは答えを各ステージノードに焼き込んだ `stage-graph.json` を出します。ワークフロー中、オーケストレータとディスパッチャはその事前解決フィールドを読みます。ワークフロー中のラーニングループ書き込みはソースを更新しますが、飛行中のコンパイル済みビューは変えません。人はすでにステージ中でオーケストレータを直しています。ルールは次のためです。次のワークフローのコンパイルが拾います。パケット飛行の途中で BGP が経路を再計算しないのと同じ形です。

### ロックと原子性

コンパイルが初日に潰すべき失敗は二つです。この実装のスウォームモードボルト向け worktree は、たいてい並列エージェントの状態を隔離します。ただし `data/stage-graph.json` はリポジトリ共有で、worktree スコープではありません。同じチェックアウトに対して二つのターミナルで `/aidlc` を出せるので、コンパイルはどちらにせよ防御が要ります。

- **並行コンパイル** は `data/stage-graph.json` への書き込みを競合させます。コンパイルは v0.4.0 から `withAuditLock`（`lib.ts`）の下で走るので、並行呼び出しは直列化します。二番目は一番目の完了を待ち、新しいソース状態に対して走ります。
- **書き込み途中のクラッシュ。** 途中で止まったコンパイルが、壊れた JSON を消費者に読ませてはいけません。コンパイルは一時ファイルへ書き、出力を検証し、POSIX `rename(2)` で原子的に改名します。読み手は前のコンパイルか新しいコンパイルのどちらかを見ます。半分書いたファイルは見ません。

どちらの型も、状態と監査の仕事ですでにコードにあります。コンパイルはそれを継ぎます。

### 二つのグラフ、二つの寿命

二つのコンパイル成果物は、消費者も更新の速さも違います。

- **`stage-graph.json`** — コントロールプレーン。ワークフロー開始でコンパイル。ワークフロー寿命のあいだ安定。読むのはオーケストレータ（DAG トポロジ、スコープルーティング）とディスパッチャ（ステージごとの `sensors_applicable`）。Claude Code の自動読み込みは、散文文脈のためにソースのルールファイルを並行で消費します。
- **`runtime-graph.json`** — データプレーン。ワークフローごとの成果物で、場所は `<record>/runtime-graph.json`。遷移クラスの監査イベントのたびに再コンパイル（監査ログのイベントソース歩き）。実行テレメトリを集約します。どのステージが走ったか、どのボルトが分岐したか、どのセンサーが発火したか、どの memory.md があるか。読むのはゲートの儀式（候補を出す）、doctor（実行の健全）、将来のワークフロー横断オブザーバ。スキーマ、コンパイル寿命、復旧モデルは [Runtime Graph](13-runtime-graph.md) です。

混ぜるとキャッシュ可能性の境界が壊れます。`stage-graph.json` はワークフロー寿命でキャッシュしたいものです。`runtime-graph.json` はイベントごとに変わります。同じ成果物にすると、データプレーンがセンサー発火を報告するたびにコントロールプレーン全体を出し直すことになります。

### ルールとセンサーが同じコンパイルを通る理由

コンパイルはコントロールプレーン入力に対して対称です。ステージ frontmatter、ルールファイル、センサーファイルは、ワークフロー開始でどれも `aidlc-graph.ts` が読み、どれもステージごとの解決済みビューに寄与します。ネットワーキングもそうです。BGP と OSPF は同じ FIB を養い、ACL とポリシーは同じフローテーブルを養います。コンパイル済みビューは一つ、ソースは複数です。

具体的には、各ステージノードにフィールドが二つ増えます。

```json
{
  "slug": "requirements-analysis",
  "phase": "inception",
  "sensors": ["required-sections", "upstream-coverage"],
  "rules_in_context": [
    {"path": "aidlc/spaces/default/memory/org.md", "scope": "org"},
    {"path": "aidlc/spaces/default/memory/team.md", "scope": "team"},
    {"path": "aidlc/spaces/default/memory/project.md", "scope": "project"},
    {"path": "aidlc/spaces/default/memory/phases/inception.md", "scope": "phase"}
  ],
  "sensors_applicable": [
    {"id": "required-sections", "path": ".claude/sensors/aidlc-required-sections.md"},
    {"id": "upstream-coverage", "path": ".claude/sensors/aidlc-upstream-coverage.md"}
  ]
}
```

`matches`（解決済みセンサーエントリにあれば）はセンサー側の能力フィルタです — *「このグロブに合うファイルをこのセンサーは分析する」* — コンパイルがマニフェストからステージの解決済みエントリへそのままスナップショットします。PostToolUse フックは発火時にそれを読み、マニフェストを開き直しません。

帰結は二つです。

- **ディスパッチャは実行時に解決歩きをしない。** ステージ入場はノードの `sensors_applicable` を読みます。すでに引き、すでに付いています。PostToolUse はこの事前解決一覧から発火します。
- **doctor と designer は解決済みビュー一つを照会する。** 「このステージに効くルールは？」「このファイルを編集するとどのセンサーが発火する？」どちらも `stage-graph.json` から直接答え、ファイルシステム歩きはしません。

### ネットワーキングの教訓を当てはめる

コントロールプレーン（コンパイル）が遅く賢い仕事を一度やり、データプレーン（オーケストレータ + ディスパッチャの読み）は解決済みビューの上で速く走ります。ワークフロー開始のコンパイルがステージごとの import をすべて解決します — すべての `sensors:` id を引き、すべての `phase:` を付け、ファイル名で万能既定ルールを拾う。ワークフロー中、実行時はグラフノードの事前解決フィールドを読みます。BGP はパケット飛行の途中で経路を再計算しません。AI-DLC もワークフローの途中で再コンパイルしません。ワークフロー中のラーニングループ書き込みはソースを更新し、コンパイル済みビューには次のワークフロー開始で入ります。

## 5. 復旧は設計から出てくる性質

いま述べたデータプレーン — `runtime-graph.json`、監査ログ、状態文書、`memory.md`、成果物の木 — には、代を払っていない性質があります。コンパクション後やきれいな再起動のあと始めた新しいハーネスセッションは、この五つをまとめて読み、前のセッションが止まったところから拾えるだけのワークフロー状態を組み立てられます。復旧は v0.5.0 に足した機能ではありません。設計のデータ規律から出てくる性質です。

### 五つのソース、一つの絵

| ソース | 残すもの | 読む順 |
|---|---|---|
| 成果物の木（`<record>/<phase>/<stage>/*.md`） | 判断そのもの、仕上がった形 | 第一 |
| ステージごとの `memory.md` | 判断の過程で気づいたこと | 第二 |
| 監査ログ（`<record>/audit/` シャード） | 各判断がいつ起き、誰が承認したか | 第三 |
| 状態文書（`<record>/aidlc-state.md`、ステージごとの状態） | ワークフローのいまの位置 | 第四 |
| `runtime-graph.json` | ステージ横断の要約（所要時間、センサー発火、学びの件数） | 第五 |

成果物が先なのは、実際に合意したものの耐久記録だからです。残り四つは旅についてです。何を考えたか、いつ起きたか、何が残っているか、ステージをまたいだ型はどう見えるか。他人の途中の仕事を拾う人も同じ順で読みます。出力、メモ、時系列、いまのカーソル、要約ビューです。

### 復旧がきれいに組み立てられるもの

判断、出力、ステージ内の文脈、時系列、いまの位置、どのボルトが分岐し何が起きたか。五つのソースを読む新しいセッションは、ワークフローが何を出したか、人が何を直したか、どのゲートが承認済みか、何が残っているか、前回がだいたいどう進んでいたかを知ります。

### 復旧が組み立てられないもの

前のセッションの会話のリズム — ステージ途中の Q&A の型、`memory.md` に残る前の LLM の作業仮説、飛行途中で切れた部分的なツール呼び出し。会話バッファはセッションと一緒に消えます。これは LLM セッションの根本性質であり、設計で直せる性質ではありません。復旧の仕事は、新しいセッションが向きを取り戻して続けられる材料を渡すことであり、前のセッションの頭の中を再現することではありません。

### 一貫の拘束

五つのソースは別のコード経路が書き、復旧が働くにはそこそこ一貫している必要があります。監査ログが正です（追記専用、「何が起きたか」の正本）。残り四つが一貫するのは、書き込みが v0.4.0 と同じ `withAuditLock` でゲートされるからです。新しいセッションは五つどれかを監査ログに照らし、ドリフトを見つけて直せます。

### フレームワークにとっての意味

フレームワークはすでに小さな版を実践しています。いまの `aidlc-state.md` はインテント作成時に書く `Scope` フィールドを持ち、セッション再開で読むので、オーケストレータが再導出しなくてもスコープはコンパクションを越えます。一般化は、データプレーンが残す耐久記録はどれも復旧面の一部であり、状態ファイルだけではない、ということです。より深い原則は、*データプレーンが復旧向けに構造化されている*ことです。耐久記録がすべて復旧面なので、再開経路はすでにある土台の上の小さな追加であり、後付けではありません。
