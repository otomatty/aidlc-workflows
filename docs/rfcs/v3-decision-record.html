01

なぜ v3 か

v2 は「モデルがステップを飛ばすたびに、機械的な強制（フック・レシート・ガード）を足す」方針で成長した。その結果、エンジンと配布物が肥大化し、AI 駆動開発そのものが重くなった。一方で README 自身が Opus 4.8 を推奨しており、強いモデル前提の設計なのに弱いモデル対策のコストを全員が払っている。

v3 は「判断はモデル、機械的処理はフック」と役割を分け、v2 の TypeScript エンジン（ルーティング・状態機械）を持たない。フックと監査ログの仕組みは踏襲するが、判断を代行させない。

両立しない2つの決定と、推奨する解

「ツール依存なし」（rev 1）と「フックを積極的に活用」「監査ログを踏襲」（rev 2）は両立しない。Claude Code と Codex のフックはプロセスを起動するので、フックを書く言語のランタイムが要る。

推奨：利用者側の実行時依存を「git ＋ フック用の最小ランタイム（bun か node のどちらか一つ）」に限定し、v2 の 10.5 万行のエンジン・状態機械・ルーティングは持たない。フックの総量には行数の予算を置く。ランタイムが無い環境でも Skill だけで一通り動くが、監査ログの自動記録とゲートの機械的な強制は失われる「縮退モード」になり、その旨を /aidlc status が表示する。

03

3つの転換

① エンジンを捨て、Git ＋ フック ＋ 監査ログに置き換える 改訂v2 の TypeScript エンジン（ルーティング・状態機械・レシート）は持たない。状態は成果物の frontmatter から導出し、証跡は git と append-only の監査ログ、機械的な検査・記録・遮断はフックが担う。最終ゲートは、人が PR をマージする行為そのもの。
② 品質は「主張 ＋ 証拠 ＋ 参照元」で保証する 改訂品質に関するすべての主張に、テスト名・コマンド出力・スクリーンショット・コミットのいずれかの証拠を付ける。すべての成果物に、どの知識（コード・設計・インフラ・背景・規約）を根拠にしたかの参照元を付ける。証拠や参照元のない主張は無効で、フックが機械的に検査する。
③ 人は Review Brief を読むコードを見なくても判断できる固定構造の文書を Verify の成果物にし、そのまま PR 本文にする。レビューが「コードを読む」から「主張と証拠を照合し、必要な質問に答える」に変わる。
04

原則と禁止リスト

P-1
判断はモデル、機械的処理はフック。手順を強制せず、禁止リストと不変条件だけを持つ。フックは判断しない。検査・記録・遮断だけを行い、判断が要る結果はモデルへ返す。改訂
P-2
成果物が状態、監査ログが証跡。状態機械を持たない。状態は成果物の frontmatter から導出し、出来事は append-only の監査ログに残す。改訂
P-3
主張には証拠を、成果物には参照元を付ける。証拠の形式を統一する（test / log / shot / commit）。参照元は パス:行@コミット か文書 ID。改訂
P-4
常時読み込むものは最小にする。専門知識は必要な時だけ読む。ただし知識レイヤーは常に最新に保つ。
P-5
根本解決の必要最小限。その場しのぎをしない。理想の設計との差分を常に意識し、根本原因を解決するのに必要な最小の変更をする。改訂
P-6
複雑性の予算を CI で守る。v2 の膨張を繰り返さない。フックにも行数の予算を置く。予算超過は Opus 5.5 での失敗の実証が条件。

禁止リスト（これ以外は禁止しない）

  • テストを通すためにテストを改変・削除する
  • 証拠を捏造する、証拠や参照元のない主張をする
  • 人の承認なしに approved にする、承認を代行する
  • 監査ログを手で書く・編集する（モデルも人も）改訂
  • 本番データに触る、main に直接 push する
  • 禁止リストに載っていないことを禁止する

守る不変条件

  • 人の承認なしに approved にならない
  • 承認済みの計画なしに実装しない
  • 契約（型・データ定義）とテストより先に実装をコミットしない 改訂
  • 作った者とは別のコンテキストで検証する
  • 受入基準がテスト・検証記録まで追跡できる
  • すべての成果物に参照元があり、参照先が存在する 改訂

禁止リストのうち機械的に判定できるもの（テストファイルの削除、main への push、監査ログの手編集、approved への無断変更）はフックが遮る。判定に判断が要るもの（その場しのぎかどうか）は reviewer が見る。

05

ライフサイクルと儀式

改訂

4ステージ。人間ゲートは Intent と Verify の2回で、Design は計画で必要と判断した時だけ行う。同期の儀式は2つ。モブ・エラボレーションは Intent と Design をまとめて1つの儀式で行い、その中に「確認点」を置いて、ある程度の粒度で人が確認できるようにする。

ステージ成果物何をするか吸収する v2 のステージ
Intent ◆intent.mdexplorer が既存コードを調査（知識レイヤーが古ければ再走査）。人と対話して受入基準（AC-n）を確定。理想形との差分・ユースケースの漏れ・リファクタ候補・根本原因を明記。Unit 分割・リスク階層・AC ごとの検証方法を提案し、確認点を経て1回の承認を得るInitialization ×3、Reverse Engineering、Requirements、User Stories、Practices Discovery、Units Generation、Delivery Planning
Design 条件付きdesign.md高リスク Unit または計画が要求した時のみ。図解を主とし、基準図との差分で示す。契約（型・データ定義・インターフェース）を先に固める。代替案とトレードオフ表を添えるDomain / Contract / Functional / NFR / Infra Design、Mockups
Build ⟳コード、テスト、build-log.mdUnit ごとに builder を worktree で並列実行。契約（型・スキーマ・データ定義が型検査と静的解析を通る）→ テスト（red）→ 実装（green）→ refactor をコミット順で証明。DoD コマンドの出力を記録。フックが順序と検査結果を監査ログに残すCode Generation、Build and Test、CI Pipeline
Verify ◆review.md、rules.md への追記別コンテキストの reviewer が敵対的に検証（破壊検査、その場しのぎの検出を含む）。Review Brief を PR 本文にして人が承認。学びを rules.md に追記reviewer 機構、sensors、governance、learnings

儀式（同期的な協働）改訂

儀式いつAI が用意するもの人が確認・決定すること
モブ・エラボレーションIntent と Design をまとめて1回（必要なら分割して継続）1画面 Intent、論点一覧、ユーザー操作のフロー図、用語集、「現状はこう動く」の証拠、理想形との差分、差分図、代替案とトレードオフ表、脅威モデル観点表（H 階層）確認点ごとに確認：AC の確定 → 非ゴール → 理想形と最小実装の線引き → Unit とリスク階層 → 設計の採択。確認は監査ログに記録

いつでもできること 改訂

脇質問

ワークフロー中に気になったことを、進行中のコンテキストに影響を与えずに聞ける。別コンテキスト（サブエージェント）が intent フォルダと知識レイヤーを読み取り専用で参照して答える。状態は変えない。質問と答えは監査ログに残るので、後で同じことを聞かれない。

/aidlc

再開

中断（セッション終了、コンテキスト圧縮、クラッシュ、意図的な停止）の後、引数なしの /aidlc でいつでも再開できる。現在地は成果物の frontmatter と監査ログの末尾から導出し、セッション開始フックが再開用の要約を渡す。/aidlc status で現在地・確認点・縮退モードの有無を見る。

テストが保証できるのは「仕様どおりに振る舞うか」だけ。次の10の次元を、それぞれ別の証拠で担保する。凡例：テストで担保できる 一部できる できない

テスト自体の品質✗破壊検査、AC カバレッジ表破壊検査の表
要件の妥当性・ユースケースの網羅 改訂✗モブ・エラボレーション、既存ユースケース × 変更の影響表、デモdecisions.md、網羅表
設計の質（境界・結合・既存構造との整合）✗図解付き設計レビュー、依存ルールの検査（フック）差分図、観点表

07

検証の方針

検証手段には優先順位がある。モデルが自動で検証できるなら、人に確認を求めない。方法の選択はモデルに任せ、禁止するのは「やってはいけないこと」だけ。

V-1 / V-2

自動で検証できるなら自動で

AC ごとに「自動テスト / AI 操作 / 人」のどれで検証するかを Intent で宣言する。テストで担保できない AC は「手動確認」と明示し、判断依頼に必ず載せる。

V-3 / V-4

方法は自由、証拠は必須

モデルは検証方法を自分で選ぶ。AI 操作による検証はスクリーンショット・ログ・実行コマンドを残す。reviewer は builder の証拠を鵜呑みにせず、自分でも再現する。

08

独立検証の仕組みとリスク階層

reviewer は builder の会話を見ない。入力は成果物と diff だけ。Claude Code で作ったものを Codex で検証する（またはその逆）ことを推奨し、モデルの多様性で同じ盲点を共有するリスクを下げる。

リスク階層で厳格さを配分する

階層はモデルが Intent で提案し、人が確認点で承認する。

階層Design破壊検査人のレビュー例
L不要なしBrief のみ文言修正、設定値、テスト追加
M任意1箇所Brief ＋ 読むべき箇所ガイドの5分版既存 API の内部変更
H必須3箇所Brief ＋ コアロジックの hunk を人が読む。モブ・コンストラクション任意認証、決済、データ移行、公開契約の変更

破壊検査（軽量ミューテーションテスト）

reviewer が「ここを壊せばテストが落ちるはずだ」という箇所を選び、実際に壊してテストを実行し、落ちたことを確認して戻す。「テストが本当に何かを検証しているか」を最も安く証明できる。

破壊した箇所期待結果
pricing.ts:41 の税率を 0 にAC-4 が落ちる落ちた
orders.ts:88 の在庫チェックを削除AC-3 が落ちる落ちなかった → 指摘 R-2
09

Git・監査ログ・フック

改訂

Intent ごとにブランチを切り、ゲートはコミット、承認は PR。状態は成果物の frontmatter から導出し、出来事は監査ログに残す。契約 → テスト → 実装 の順序はコミット履歴が証明し、フックが検査する。

監査ログ（v2 の仕組みを踏襲）

  • Intent ごとに append-only。イベント種別は正典の台帳で管理し、勝手に増やさない（v2 と同じ）
  • 書くのはフックだけ。モデルも人も手で書かない（禁止リスト）。v2 の「ツール所有の記録」と同じ考え方
  • 種別は v2 の 91 種から必要最小限に絞る。残す候補：ライフサイクル遷移、確認点の確認、ゲート決定、質問と回答（脇質問を含む）、フックの検査結果（契約・DoD・鮮度・引用）、知識レイヤーの更新、reviewer の受け渡し
  • 監査ログと decisions.md の関係：監査ログは出来事の機械的な記録、decisions.md は人が読む判断の記録。decisions.md への追記も監査ログに残る
  • v2 の record を移行する時は、audit シャードも v3 の台帳に変換して引き継ぐ（§14）

フックが担う機械的処理

境界は一つ：フックは判断しない。検査・記録・遮断だけを行い、判断が要る結果はモデルへ返す。v2 が判断まで代行させて膨らんだ反省から、フックの総量にも行数の予算を置く。

機械的処理フックがすることモデル（または人）が判断すること
監査イベントの記録遷移・確認・決定・質問・検査結果を append-only に書く—
承認の真正性status: approved への変更を、人の決定が監査ログにある時だけ通す承認するかどうかは人
契約 → テスト → 実装 の順序型検査・静的解析・スキーマ検証を実行して記録。順序違反のコミットを遮る何を契約として固めるかはモデル
DoD の実行と記録rules.md のコマンドを実行し、出力を build-log と監査ログに残す失敗の原因分析と修正はモデル
知識の鮮度チェックcodekb の世代と git HEAD、設計・インフラ文書の更新日を比べ、古ければ印を付ける再走査の範囲は explorer
引用検査成果物の「参照元」の参照先が存在し、最新世代かを検査何を引用するかはモデル
禁止リストの機械的部分テストファイルの削除・改変、main への push、監査ログの手編集を遮る例外を認めるかは人
セッション開始・再開成果物と監査ログから現在地を復元し、再開用の要約を渡す次に何をするかはモデル
状態表示statusline に現在の Intent・ステージ・確認点・縮退モードの有無を出す—
10

知識の鮮度と参照元

改訂

既存コード・設計・インフラ・プロジェクト背景・コーディング規約を「知識レイヤー」として常に最新に保ち、AI のすべての成果物に、どの知識を根拠にしたかの参照元を必ず載せる。鮮度と引用の検査はフックが行い、再走査は explorer が行う。

知識レイヤーに入るもの

  • 既存コード：explorer の調査結果（構造、依存、基準となるアーキテクチャ図、用語集）と世代（コミット）
  • 設計：design 文書、契約（型・スキーマ・インターフェース）、過去の Intent の design.md
  • インフラ：構成・環境・デプロイ方法（Operation は対象外だが、実装が依存する情報は持つ）
  • プロジェクト背景：目的、制約、用語、関係者
  • コーディング規約：rules.md（DoD、禁止リスト、Corrections、依存ルール）

参照元のルール

  • すべての成果物に ## 参照元 を置く。空は不可
  • 書式は パス:行@コミット か 文書#節@日付。フックが参照先の存在と世代を検査する
  • Review Brief の「主張と証拠」に加えて「根拠にした知識」を人が辿れる
  • 知識が古いまま成果物を書いたら、鮮度チェックが監査ログに残し、Brief に警告が載る
  • Learn で rules.md に追記した内容も、次の Intent から参照元になる
11

根本解決と最小実装

改訂

既存プロジェクトでは「どう作るのが設計として理想か」を常に問い、ユースケースの漏れとリファクタできる箇所を意識し、その場しのぎではなく根本原因を解決する、必要最小限の実装をする。「最小」とは、根本原因を解決するのに必要な最小の変更であり、将来のための汎化はしない。

Intent / Design に必ず含めるもの

  • 理想形：このコードベースで理想的な作り方と、その根拠（参照元つき）
  • 現状との差分：理想形と現状のずれ。今回埋めるもの／埋めないもの
  • ユースケース網羅表：既存ユースケース × 今回の変更の影響。漏れの候補
  • リファクタ候補：今やる（根本原因に関わる）／後回し（理由と記録先）
  • 根本原因分析（バグ修正）：なぜ起きたか、同種の箇所が他にないか
  • 最小実装の線引き：必要なもの／意図的にやらないもの。確認点で人が確認する

reviewer が検出する「その場しのぎ」

  • 特殊ケースの分岐を足して根本原因に触れていない
  • エラーの握りつぶし、リトライで隠す
  • 既存ロジックの複製（共通化すべきものを重複させる）
  • 型の緩和（any 化、キャスト）、静的解析の抑制コメント
  • テストのスキップ・条件の緩和
  • 理想形との差分に書かれていない設計上の妥協

これらは判断が要るのでフックではなく reviewer の観点表で見る。検出した項目は Brief の「主張と証拠」の反例として載せ、人が最終判断する。

Review Brief と図解

Verify の成果物 review.md は固定構造で、1〜4 節にはコードを一切書かない。読む人が深さを選べるように、各節に読む深さを付ける。

図解の原則

  • 1変更1図：変更したフローには必ず図を付ける
  • 差分は色で：基準図（知識レイヤー）に対して追加・変更・削除を色分けする
  • 詳細度は段階化：コンテキスト → コンポーネント → シーケンス → データ／状態の順で、読む人が深さを選ぶ
  • Mermaid で Markdown 内に置く：GitHub でそのまま見える。設計パックは単一 HTML でも出力する

レビュー負荷を下げる工夫

  • 人は主張を読み、証拠と参照元の存在で信頼する。疑わしい行だけ抜き取り検査する
  • 受動的な「全部読む」を、能動的な「質問に答える」に変える。質問の数は制限しないが、答え済みは再質問しない
  • builder と reviewer の2つの独立した記述を並べ、食い違いを見るべき場所として示す
  • デモ手順（demo.sh、curl、操作手順）を添え、人が自分で叩ける
  • Intent ゲートも同じ思想で「1画面」に収める

v2 record からの移行

移行は Skill（/aidlc migrate）。モデルが v2 record を読み、v3 の intent フォルダを生成し、移行レポートを Review Brief の形式で出して人が承認する。「元ファイル → 行き先」の全件表を載せ、行き先のないファイルを明示する。元の record は aidlc/archive/v2/ に残す。

aidlc-state.md のチェックボックス→各成果物の status:。Intent / Design / Build / Verify のどこまで済んだか
ideation/*（intent-statement、scope-document …）→intent.md § 背景（付録）と knowledge/background.md
requirements.md ＋ user-stories→intent.md § 受入基準。ストーリーの受入条件から AC-n を採番
domain-design、contract-design、units-generation、bolt-plan→design.md ＋ intent.md の実行計画（Unit とリスク階層）。契約は knowledge/design/ にも
construction/<unit>/ の functional / nfr / infra design→design.md § Unit 別付録。インフラは knowledge/infra/ にも
code-generation の ## Review 付録→review.md（履歴として）

memory/{org,team,project}.md、phases/*.md→rules.md に統合。チームが affirm していない org 既定は落とす

未決事項と次のステップ

次に決めること

Q1
フック用ランタイム：bun / node のどちらか。ランタイムが無い環境の縮退モードを認めるか（§2 の推奨で進めてよいか）改訂
Q2
監査イベントの最小集合：v2 の 91 種からどれを残し、何を足すか改訂
Q3
確認点の粒度の既定：AC グループごと / Unit ごと / 設計セクションごと改訂
Q4
多層品質モデルの各層を、どのリスク階層で必須にするか（例：セキュリティ観点表は H のみ、契約の整合は全階層）
Q5
図の標準セット：コンテキスト / コンポーネント / シーケンス / データ / 状態のうち、Intent・Design・Brief でそれぞれ何を必須にするか
Q6
AI 操作による検証の環境：ブラウザ操作やアプリ起動をどこで行うか（ローカル、コンテナ、CI）
Q7
Brief の言語：日本語固定か、rules.md で選択か

進め方

  1. 未決事項 Q1〜Q7 を決める（Q1 が設計の前提になる）
  2. 設計レベルへ落とし込む：Skill の構成、成果物テンプレート、監査イベント台帳、フック一覧と予算、知識レイヤーの形式、Brief の書式、移行の手順
  3. Claude Code 向けプロトタイプ：SKILL.md、3エージェント、フック、Review Brief テンプレート
  4. 評価スイートで v2 と比較し、「判断はモデル、機械的処理はフック」の分担が成り立つか確かめる
  5. Codex へ展開し、移行 Skill を整備して v3.0.0
