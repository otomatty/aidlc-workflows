03

3つの転換

① Git がエンジン状態ファイル・監査ログ・フック・レシートを全廃し、ブランチ・コミット・PR で代替する。監査証跡は git log。最終ゲートは、人が PR をマージする行為そのもの。
② 品質は「主張 ＋ 証拠」で保証する品質に関するすべての主張に、テスト名・コマンド出力・スクリーンショット・コミットのいずれかの証拠を付ける。証拠のない主張は無効。モデルの「やりました」を信じる必要がなくなる。
③ 人は Review Brief を読むコードを見なくても判断できる固定構造の文書を Verify の成果物にし、そのまま PR 本文にする。レビューが「コードを読む」から「主張と証拠を照合し、3問に答える」に変わる。
04

原則と禁止リスト

P-1
モデルを信頼し、不変条件だけ守る。手順を強制せず、禁止リストだけを持つ。それ以外はモデルが判断する。
P-2
成果物が状態である。状態機械・監査ログ・フックを持たない。
P-3
主張には証拠を付ける。証拠の形式を統一する（test / log / shot / commit）。
P-4
常時読み込むものは最小にする。専門知識は必要な時だけ読む。
P-5
複雑性の予算を CI で守る。v2 の膨張を繰り返さない。予算超過は Opus 5.5 での失敗の実証が条件。

禁止リスト（これ以外は禁止しない）

  • テストを通すためにテストを改変・削除する
  • 証拠を捏造する、証拠のない主張をする
  • 人の承認なしに approved にする、承認を代行する
  • 本番データに触る、main に直接 push する
  • 禁止リストに載っていないことを禁止する

守る不変条件（4つ）

  • 人の承認なしに approved にならない
  • 承認済みの計画なしに実装しない
  • 作った者とは別のコンテキストで検証する
  • 受入基準がテスト・検証記録まで追跡できる
05

ライフサイクルと儀式

4ステージ。人間ゲートは既定で Intent と Verify の2回。Design は計画で必要と判断した時だけ行う。同期の儀式（モブ）は3つで、AI が事前資料・論点・議事録・決定の反映を担う。

ステージ成果物何をするか吸収する v2 のステージ
Intent ◆intent.mdexplorer が既存コードを調査。人と対話して受入基準（AC-n）を確定。Unit 分割・リスク階層・AC ごとの検証方法を提案し、1回の承認を得る。1画面に収めるInitialization ×3、Reverse Engineering、Requirements、User Stories、Practices Discovery、Units Generation、Delivery Planning
Design 条件付きdesign.md高リスク Unit または計画が要求した時のみ。図解を主とし、基準図との差分で示す。代替案とトレードオフ表を添えるDomain / Contract / Functional / NFR / Infra Design、Mockups
Build ⟳コード、テスト、build-log.mdUnit ごとに builder を worktree で並列実行。red → green → refactor をコミット順で証明。DoD コマンドの出力を記録Code Generation、Build and Test、CI Pipeline
Verify ◆review.md、rules.md への追記別コンテキストの reviewer が敵対的に検証（破壊検査を含む）。Review Brief を PR 本文にして人が承認。学びを rules.md に追記reviewer 機構、sensors、governance、learnings

儀式（同期的な協働）

儀式いつAI が用意するものその場で決めること
モブ・エラボレーション①Intent の途中1画面 Intent、論点一覧、ユーザー操作のフロー図、用語集、「現状はこう動く」の証拠AC の確定、非ゴール、リスク階層
モブ・エラボレーション②Design の途中（必要時）差分図、代替案2つまでとトレードオフ表、脅威モデル観点表（H 階層）設計の採択
モブ・レビューVerify の後Review Brief、AI 操作によるデモ、判断依頼3問3問への回答、PR 承認、末尾5分で振り返り

非同期でも回せる：事前読み → 同期で決定 → 事後反映。決定は decisions.md に人の言葉で記録し、承認の根拠にする。H 階層の Unit ではモブ・コンストラクション（AI の構築を同期で見て方向修正）を任意で行う。

06

品質モデル — テストだけでは足りない

テストが保証できるのは「仕様どおりに振る舞うか」だけ。次の9つの次元を、それぞれ別の証拠で担保する。凡例：テストで担保できる 一部できる できない

品質の次元テスト担保手段証拠の形式
正しさ（仕様どおり動く）○AC に紐づくテスト、DoDtest / log
テスト自体の品質✗破壊検査、AC カバレッジ表破壊検査の表
要件の妥当性✗モブ・エラボレーション、デモ、振る舞い差分の確認decisions.md
設計の質（境界・結合・既存構造との整合）✗図解付き設計レビュー、依存ルールの検査差分図、観点表
保守性（可読性・命名・重複・規約）△静的解析、規約監査、reviewer の観点表log、観点表
セキュリティ△依存監査、脅威モデル観点表（リスク階層に応じて）log、観点表
非機能（性能・リソース）△計測を証拠として要求log
実使用での問題（未知の未知）✗AI がアプリを実際に操作する探索的検証shot / log
判断の質（なぜそう決めたか）✗決定ログ、代替案の記録decisions.md

証拠の書式は統一する：test:ファイル › テスト名、log:build-log#L行、shot:画像パス、commit:ハッシュ。

07

検証の方針

検証手段には優先順位がある。モデルが自動で検証できるなら、人に確認を求めない。方法の選択はモデルに任せ、禁止するのは「やってはいけないこと」だけ。

V-1 / V-2

自動で検証できるなら自動で

AC ごとに「自動テスト / AI 操作 / 人」のどれで検証するかを Intent で宣言する。テストで担保できない AC は「手動確認」と明示し、判断依頼に必ず載せる。

V-3 / V-4

方法は自由、証拠は必須

モデルは検証方法を自分で選ぶ。AI 操作による検証はスクリーンショット・ログ・実行コマンドを残す。reviewer は builder の証拠を鵜呑みにせず、自分でも再現する。

08

独立検証の仕組みとリスク階層

reviewer は builder の会話を見ない。入力は成果物と diff だけ。Claude Code で作ったものを Codex で検証する（またはその逆）ことを推奨し、モデルの多様性で同じ盲点を共有するリスクを下げる。

リスク階層で厳格さを配分する

階層はモデルが Intent で提案し、人が承認する。

階層Design破壊検査人のレビュー例
L不要なしBrief のみ文言修正、設定値、テスト追加
M任意1箇所Brief ＋ 読むべき箇所ガイドの5分版既存 API の内部変更
H必須3箇所Brief ＋ コアロジックの hunk を人が読む。モブ・コンストラクション任意認証、決済、データ移行、公開契約の変更

破壊検査（軽量ミューテーションテスト）

reviewer が「ここを壊せばテストが落ちるはずだ」という箇所を選び、実際に壊してテストを実行し、落ちたことを確認して戻す。「テストが本当に何かを検証しているか」を最も安く証明できる。

破壊した箇所期待結果
pricing.ts:41 の税率を 0 にAC-4 が落ちる落ちた
orders.ts:88 の在庫チェックを削除AC-3 が落ちる落ちなかった → 指摘 R-2
09

Git がエンジン

Intent ごとにブランチを切り、ゲートはコミット、承認は PR。状態は成果物の frontmatter から導出する。テスト先行の順序はコミット履歴が証明する。

10

Review Brief と図解

Verify の成果物 review.md は固定構造で、1〜4 節にはコードを一切書かない。読む人が深さを選べるように、各節に読む深さを付ける。

1画面

1画面

読むべき箇所ガイド5分版 / 15分版。hunk を core / plumbing / tests / generated / rename に分類し、読まなくてよいものを明示
5分 H は 15分

図解の原則

  • 1変更1図：変更したフローには必ず図を付ける
  • 差分は色で：基準図（codekb）に対して追加・変更・削除を色分けする
  • 詳細度は段階化：コンテキスト → コンポーネント → シーケンス → データ／状態の順で、読む人が深さを選ぶ
  • Mermaid で Markdown 内に置く：GitHub でそのまま見える。設計パックは単一 HTML でも出力する（ツール不要）

レビュー負荷を下げる工夫

  • 人は主張を読み、証拠の存在で信頼する。疑わしい行だけ抜き取り検査する
  • 受動的な「全部読む」を、能動的な「3問に答える」に変える
  • builder と reviewer の2つの独立した記述を並べ、食い違いを見るべき場所として示す
  • デモ手順（demo.sh、curl、操作手順）を添え、人が自分で叩ける
  • Intent ゲートも同じ思想で「1画面」に収める

配布物 — Markdown のみ

利用者側の実行時依存はゼロ。配布物は AGENTS.md、Skill、エージェント定義だけ。このリポジトリ側は core/ に一度書き、2ハーネスへコピーするだけにする（利用者はスクリプトを実行しない）。

12

v2 record からの移行

移行もツールではなく Skill。モデルが v2 record を読み、v3 の intent フォルダを生成し、移行レポートを Review Brief の形式で出して人が承認する。「元ファイル → 行き先」の全件表を載せ、行き先のないファイルを明示する。元の record は aidlc/archive/v2/ に残す。

v2 の成果物v3 の行き先
aidlc-state.md のチェックボックス→各成果物の status:。Intent / Design / Build / Verify のどこまで済んだか
ideation/*（intent-statement、scope-document …）→intent.md § 背景（付録）
requirements.md ＋ user-stories→intent.md § 受入基準。ストーリーの受入条件から AC-n を採番
domain-design、contract-design、units-generation、bolt-plan→design.md ＋ intent.md の実行計画（Unit とリスク階層）
construction/<unit>/ の functional / nfr / infra design→design.md § Unit 別付録
code-generation の ## Review 付録→review.md（履歴として）
audit/*.md→decisions.md。人の決定（承認・却下・質問への回答）だけを抽出
memory/{org,team,project}.md、phases/*.md→rules.md に統合。チームが affirm していない org 既定は落とす
codekb/<repo>/→aidlc/codekb/<repo>/ にそのまま
operation/*→archive/v2/ にのみ残す

14

未決事項と次のステップ

次に決めること

Q1
多層品質モデルの各層を、どのリスク階層で必須にするか（例：セキュリティ観点表は H のみ、保守性は全階層）
Q2
図の標準セット：コンテキスト / コンポーネント / シーケンス / データ / 状態のうち、Intent・Design・Brief でそれぞれ何を必須にするか
Q3
儀式の回数の既定：モブ・エラボレーション①②とモブ・レビューを毎回行うか、リスク階層で省略できるか
Q4
AI 操作による検証の環境：ブラウザ操作やアプリ起動をどこで行うか（ローカル、コンテナ、CI）
Q5
Brief の言語：日本語固定か、rules.md で選択か

進め方

  1. 未決事項 Q1〜Q5 を決める
  2. 設計レベルへ落とし込む（Skill の構成、成果物テンプレート、Brief の書式、移行の手順）
  3. Claude Code 向けプロトタイプ：SKILL.md、3エージェント、Review Brief テンプレート
  4. 評価スイートで v2 と比較し、「強いモデルを信頼する」賭けが成り立つか確かめる
  5. Codex へ展開し、移行 Skill を整備して v3.0.0
